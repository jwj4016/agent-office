# Agent Office 개발 계획 — Go + Wails

수정일: 2026-10-02  
대상: Windows · macOS · Linux  
이 문서는 구현할 기능을 정한 계획이다. 현재 도트 시안은 시뮬레이션이며 실제 AI 연결과 사람 업무 실행은 아직 구현되지 않았다.

## 1. 앱의 목적

사용자가 회사의 역할과 업무 프로세스를 만들고, 각 업무를 AI 또는 사람에게 배정해 하나의 결과물을 완성하는 데스크톱 앱을 만든다.

귀여운 도트 사무실에서는 담당자의 실제 업무 상태를 보여준다. 기획·개발뿐 아니라 법률 검토, 시장 분석, 부동산 분석 등 서로 다른 프로세스를 사용할 수 있다.

## 2. 핵심 사용 방식

| 사용 방식 | 앱의 동작 |
|---|---|
| 사용자가 직접 설계 | 역할·지침·프로세스를 만들면 앱이 담당 AI를 연결하고 정해진 순서와 조건에 따라 실행한다. 사람에게 맡긴 단계는 사람이 수행한다. |
| AI가 설계·배정 | 사용자가 목표를 요청하면 설계 AI가 필요한 역할·지침·프로세스를 만들고 담당자를 배정한다. 기존 조직을 먼저 활용하고 부족한 역할을 추가한다. |
| AI와 사람이 협업 | 업무별 담당자를 AI 또는 사람으로 선택한다. 사람은 승인뿐 아니라 코드 리뷰·자료 조사·문서 작성 등 실제 업무도 수행한다. |
| 서비스를 나누어 관리 | 게임 개발·부동산 분석 서비스 개발 등을 별도 서비스 프로젝트로 만들고 각각의 조직 배정·프로세스·자료·실행 상태를 관리한다. |

‘역할’은 책임과 지침이고, ‘담당자’는 그 역할을 맡는 AI 또는 사람이다. 같은 역할의 업무라도 프로젝트나 단계에 따라 다른 담당자를 지정할 수 있다. 조직의 상하 관계는 지침·보고 관계를 정하고, 업무의 실행 순서는 프로세스가 정한다.

### A. 사용자가 직접 만드는 경우

1. 기획자·CTO·개발자·법률 담당자 등 역할과 하위 역할을 만든다.
2. 역할별 지침과 기본 담당자, AI 공급자·모델을 설정한다.
3. 업무의 순서, 병렬 처리, 입력·산출물, 완료 기준을연결한다.
4. 실행을 시작하면 앱이 준비된 업무를 해당 담당자에 게 전달한다.
5. 결과를 저장하고 다음 업무에 전달한다.

AI 담당자는 업무가 있을 때 실행한다. 역할 수만큼 AI 프로세스를 항상 켜두지는 않는다.

### B. 요청만 입력하는 경우

예: “작은 웹 게임을 출시하고 싶어. 코드 리뷰는 내가 할게.”

설계 AI가 목표를 분석해 기획·시장 분석·법률 검토·개발·리뷰·출시 준비를 구성하고, 코드 리뷰에는 사용자를 배정한다. 각 업무의 지침, 입력 자료, 결과 형식과 승인 지점까지 제안한다.

두 가지 실행 모드를 제공한다.

- 검토 후 실행: 생성된 조직과 흐름을 사용자가 수정·확정한 뒤 시작한다. 기본 모드다.
- 자동 구성·실행: 사용자가 미리 허용한 도구·예산·작업 범위 안에서 조직과 흐름을 자동 적용하고 시작한다. 사람이 맡은 업무와 명시된 승인 지점에서는 기다린다.

연결되지 않은 도구, 담당자 없는 업무, 잘못된 의존 관계는 실행 전에 표시한다. 실행 중 새로운 업무가 필요하면 변경 내용을 제안하고 선택한 모드와 정책에 따라 적용한다. 사용자가 검토 중인 기존 결과를 몰래 교체하지 않는다.

### C. 사람이 업무를 맡는 경우

예시 흐름:

    기획(AI) → 기획 승인(나) → 설계(AI)
    → 백엔드·프론트엔드 개발(AI) → 코드 리뷰(나)
    → QA(AI) → 출시 승인(나)

코드 리뷰에 도달하면 변경 내역과 테스트 결과를 사용자의 할 일로 제공한다. 사용자는 직접 검토하고 ‘통과’ 또는 ‘수정 요청’을 남긴다. 수정 요청은 해당 개발 AI에게 전달되고, 수정 후 다시 리뷰를 요청한다.

사람 업무에는 담당자, 필요한 자료, 결과 제출 방식, 완료 기준을 설정한다. AI도 사람에게 질문할 수 있고, 사람도 AI에게 수정 의견을 전달할 수 있다. 대기 중인 업무와 무관한 병렬 업무는 계속 진행한다.

첫 버전의 사람 담당자는 앱 사용자 본인이다. 여러 사람의 계정·원격 배정·공동 작업은 후속 버전으로 확장한다.

### D. 여러 서비스를 관리하는 경우

관리 구조는 ‘회사 → 서비스 프로젝트 → 업무 프로세스 → 실행 기록’으로 한다. 서비스 하나를 프로젝트 하나로 관리하고, 그 안에 개발·법률 검토·시장 분석 등 여러 프로세스와 반복 실행 기록을 둔다.

| 서비스 프로젝트 | 업무 프로세스 예시 |
|---|---|
| 게임 서비스 | 게임 개발, 출시 전 검토, 업데이트 |
| 부동산 분석 서비스 | 서비스 개발, 데이터 품질 검토, 분석 보고서 |

- 서비스별 목표·담당자·지침·프로세스·자료·코드 저장소·예산·승인·산출물·도트 사무실을 분리한다.
- 회사 공통 역할과 지침은 재사용할 수 있지만, 담당자 배정·AI 세션·대화·기억은 서비스별로 분리한다. 공유할 자료는 사용자가 명시적으로 선택한다.
- 전체 대시보드에서 서비스별 진행 상황을 보고, 사용자의 할 일에는 서비스 이름을 표시한다.
- 서비스를 전환해도 진행 중인 실행은 유지한다. 서비스별 시작·일시 정지·중단을 지원하고 전체 동시 실행 한도도 적용한다.
- “새 부동산 분석 서비스를 만들어줘” 같은 요청은 새 프로젝트에 구성한다. 기존 서비스에 업무를 추가하는 요청은 지정한 프로젝트에 적용한다.

## 3. 기술 구성

| 영역 | 선택 |
|---|---|
| 데스크톱 앱 | Go + Wails v2 안정 버전 |
| 화면 | React + TypeScript |
| 업무 편집기 | React Flow |
| 도트 사무실 | Canvas 2D + CSS |
| 업무 실행 엔진 | Go |
| 로컬 저장 | SQLite, Go 드라이버는 기술 실증에서 확정 |
| AI 연결 | Codex App Server, Claude CLI·Agent SDK, OpenAI·Claude API |
| 코드 작업 관리 | Git 작업 공간 분리와 통합 |
| 배포 | Wails 빌드와 운영체제별 설치 패키징 |

Wails는 Go와 웹 화면을 연결하고 Windows·macOS·Linux를 지원한다. 공식 문서상 Wails v2는 안정 버전이고 v3는 베타이므로 초기 제품은 v2로 시작한다. [Wails 소개](https://v2.wails.io/docs/introduction/), [버전 상태](https://v3.wails.io/faq/)

화면은 필요한 Go 함수만 호출하고, Go는 저장된 실행 상태를 이벤트로 화면에 전달한다. 업무 실행·파일 접근·자격증명은 Go 쪽에서 관리한다. [Wails 이벤트](https://v2.wails.io/docs/reference/runtime/events/)

Claude Agent SDK의 TypeScript·Python 기능이 필요하면 별도 실행 프로그램을 연결한다. 앱 전체를 Go로 바꾸더라도 공급자 실행 환경은 따로 관리한다. [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)

프로젝트 기록은 로컬에 저장하고 AI 작업에 필요한 입력만 공급자로 전송한다. API 키는 OS의 비밀정보 보호 기능을 이용하며 로그·템플릿·내보내기에서 제외한다.

목표는 앱의 기본 자원 사용량을 줄이는 것이다. 성능은 화면과 AI 하위 프로세스를 포함해 측정하고, 언어 선택만으로 AI 응답 속도 향상을 보장하지 않는다.

## 4. 핵심 화면

| 화면 | 주요 기능 |
|---|---|
| 서비스 대시보드 | 서비스 프로젝트 생성·전환, 전체 진행 상황과 대기 업무 |
| 조직 관리 | 역할·하위 역할·지침, AI 또는 사람 담당자 설정 |
| 요청 화면 | 자연어 목표 입력, AI 조직·프로세스 생성 |
| 프로세스 편집 | 순서·병렬·조건·입출력·담당자·승인 지점 편집 |
| 도트 사무실 | 실제 작업·회의·대기·완료·오류 상태 |
| 내 할 일·승인함 | 사람 업무 수행, 결과 제출, 승인·반려 |
| 결과·실행 기록 | 문서, 질문·답변, 결정, 코드 변경, 테스트 결과 |

사용자와 AI 담당자를 화면에서 구분한다. 사람이 검토 중이라고 등록하면 해당 캐릭터에 검토 상태를 표시하되, 앱 밖에서 실제 무엇을 하는지 추정하지 않는다.

## 5. 실행 규칙

- AI 업무: 실행 → 산출물 생성 → 완료 기준 검증 → 다음 업무.
- 사람 업무: 할 일 전달 → 사람의 결과 제출·완료 결정 → 다음 업무.
- 승인: 지정된 결과에 대해 승인·반려·보류를 기록한다.
- 반려: 수정 의견을 담당자에게 전달하고 영향을 받는 후속 결과를 재검토한다. 이전 결과는 보존한다.
- 협업: 담당자 간 질문·답변·검토·결정을 관련 업무와 산출물에 연결한다.
- 버전: 실행에 사용한 조직·지침·흐름은 고정하고 변경은 새 버전으로 기록한다.
- 병렬 개발: 별도 Git 작업 공간을 사용하고 통합 후 테스트·빌드한다.
- 복구: 중단·오류·재시작 후 기록과 부분 결과를 보존한다. 불명확한 외부 조치를 자동 중복 실행하지 않는다.
- 제한: 예산·동시 실행·재시도·수정 횟수를 설정한다. 사람의 무응답을 자동 승인으로 간주하지 않는다.
- 공개: 기획 승인과 실제 배포 승인을 구분한다. 초기에는 출시 패키지와 안내를 제공하고 검증된 배포 연결부터 자동화한다.

## 6. 개발 순서

| 단계 | 구현 | 완료 기준 |
|---|---|---|
| 1. 기술 실증 | 세 플랫폼 Wails 앱, AI 실행·취소, 저장 | 설치 파일에서 실제 작업과 결과 저장 성공 |
| 2. 기본 업무 | 서비스 프로젝트 분리·조직·프로세스·AI/사람 배정·승인·반려 | 서비스별 흐름대로 AI와 사람이 작업하고 자료·기록이 섞이지 않음 |
| 3. AI 설계 | 자연어 요청에서 역할·흐름·담당자 생성 | 검토 모드와 사전 허용 범위의 자동 실행 동작 |
| 4. 협업 | 질문·결정 기록, 병렬 개발, 통합·검증 | 여러 담당자가 하나의 결과물을 완성 |
| 5. 제품화 | 도트 사무실, 템플릿, 복구, 성능·설치 검증 | 세 플랫폼에서 핵심 사용자 여정 통과 |

기술 실증은 1~2주를 목표로 한다. 전체 일정은 Go/Wails 경험과 플랫폼별 AI 연결 결과를 확인한 뒤 산정한다. 초기 동시 실행은 2개로 시작한다.

첫 실제 프로젝트는 ‘기획 AI → 사용자 승인 → 개발 AI → 사용자 코드 리뷰 → QA AI → 결과 전달’로 한다. 이어서 게임 출시·법률 검토·부동산 분석·빈 흐름 템플릿을 추가한다.

## 7. 첫 출시의 완료 기준

1. 사용자가 만든 조직과 프로세스가 실제 AI 실행에 적용된다.
2. 자연어 요청으로 역할·지침·흐름·담당자를 생성하고 편집할 수 있다.
3. 코드 리뷰 등 실제 업무를 사람이 맡아 AI와 협업할 수 있다.
4. 승인·반려·질문·재작업이 올바른 업무와 결과 버전에 반영된다.
5. 도트 사무실은 실제 상태를 표시하고 재시작 후 기록이 복원된다.
6. Windows·macOS·Linux의 명시된 지원 환경에서 설치와 핵심 기능을 검증한다.
7. 여러 서비스를 독립적으로 실행·중단하고, 전환 후에도 상태를 복원하며 서비스 간 자료·AI 세션이 의도 없이 섞이지 않는다.

회원가입 없이 로컬 사용부터 시작한다. 여러 사용자 협업, 클라우드 동기화, 원격 실행, 자유로운 사무실 꾸미기는 후속 단계로 둔다.

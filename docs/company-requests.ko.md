# 회사 요청 사용 안내 — 회사에 말로 맡기면 접수 담당이 처리한다

회사나 서비스에 하고 싶은 일을 말로 적으면, 접수 담당 AI가 읽고 처리 방법을 정합니다. 사람은 부서를 골라 업무를 만들거나 결과 코드를 git으로 직접 꺼내지 않아도 됩니다. 설계와 단계별 기록은 [계획서](plan/company-requests/plan.md)와 [진행 기록](plan/company-requests/progress.md)에 있습니다.

## 접수 담당

| 접수 담당 | 하는 일 | 정하는 곳 |
|---|---|---|
| 회사 접수 담당(기본 이름 ‘비서실’) | 요청이 어느 서비스의 일인지 가려 그 서비스의 접수 담당에게 넘깁니다. 회사 전체에 관한 질문에는 바로 답합니다. | ‘회사 조직’ 화면의 ‘회사 접수 담당’ — AI 연결·모델·지침·월 예산 |
| 서비스 접수 담당 | 서비스 안에서 답하거나, 업무를 제안하거나, 회사 조치를 제안하거나, 되묻습니다. | 서비스의 ‘부서·담당자’ 탭의 ‘접수 담당’ — 서비스의 AI 담당자 한 명과 접수 지침 |

- **접수 담당이 없으면 AI가 배치합니다.** 접수 담당 없이 요청이 오면 AI가 서비스(목표·지침·부서·담당자·최근 실행)를 분석해 접수 담당의 이름과 그 서비스 전용 지침을 쓰고, 앱이 새 AI 담당자로 만들어 이어서 처리합니다. 요청 카드에 “AI가 ‘…’를 새로 배치했습니다”가 보입니다. 회사 접수 담당도 같은 방식으로 배치합니다.
  - 새 담당자는 회사 공통 역할 ‘접수 담당’(처음 한 번 만들어짐)에 배정되고, 서비스마다 다른 점은 담당자 지침에 들어갑니다.
  - AI 연결은 그 서비스의 AI 담당자가 가장 많이 쓰는 검증된 연결로 앱이 정합니다. 검증된 연결이 없으면 ‘접수 담당 필요’로 기다립니다.
  - 요청 하나에 자동 배치는 2번까지 시도하고, 실패하면 이유를 남기고 사람을 기다립니다.
- **직접 정할 수도 있습니다.** 서비스의 ‘부서·담당자’ 탭 ‘접수 담당’에서 ‘AI에게 맡기기’, ‘새로 만들기’(이름·연결·모델·지침), ‘기존 인원 중 지정’ 중 하나를 고릅니다. 정한 뒤에는 ‘AI로 지침 다시 쓰기’로 서비스가 바뀐 만큼 지침을 고칠 수 있습니다. 회사 접수 담당은 ‘회사 조직’ 화면에서 같은 버튼을 씁니다.
- ‘사용 안 함’으로 둔 접수 담당과, 사람으로 바뀐 담당자는 자동으로 바꾸지 않고 ‘접수 담당 필요’로 기다립니다.
- 접수 담당은 파일을 읽거나 명령을 실행하지 않습니다. 앱이 서비스 정보(목표·지침, 부서·담당자, 진행 중인 업무, 최근 실행과 코드 결과, 최근 결과의 요약, 확정된 업무 흐름)를 요약해 넘기고, 그 안의 것만 씁니다. 목록에 없는 부서·담당자·실행·결과를 가리키면 그 판단은 실패로 처리되어 다시 묻습니다.

## 조직: 부서와 접수 담당

- **새 서비스는 조직까지 함께 만듭니다.** ‘새 목표’ 설계안에 역할·담당자·업무 흐름과 함께 **부서**(이름, 책임, 구성원, 대표, 받아 볼 사건)와 **접수 담당**이 들어갑니다. 검토 화면의 ‘부서와 접수 담당’에서 보고 적용합니다.
- **자동 모드 서비스의 부서는 스스로 일을 시작합니다.** 자동 시작, 결과 초안 공유, 참고용 협업 결정을 켠 채로 만들어집니다. 쓰는 연결과 예산은 서비스의 자동 실행 범위(허용한 연결, 서비스 예산)를 따릅니다. 검토 모드면 모두 꺼진 채로 만들어집니다.
- **이미 있는 서비스는 ‘조직 정비’를 씁니다.** 서비스의 ‘부서·담당자’ 탭에서 ‘AI에게 조직 제안받기’를 누르면, AI가 아직 부서에 없는 담당자를 부서로 묶고 접수 담당이 없으면 함께 제안합니다. 미리보기를 보고 ‘적용’합니다.
  - 자동 모드인데 자동 실행에 허용된 연결이 없으면, 부서 구성원이 쓰는 연결을 허용할지 고르게 합니다(기본은 허용).
  - 예산이 없으면 그 사실을 보여 줍니다. 예산이 없으면 업무가 자동으로 시작하지 않고 ‘자동 시작 검토’로 내 할 일에 올라옵니다. 예산은 앱이 정하지 않습니다.
  - 적용하면 부서가 없던 진행 전 업무가 담당자의 새 부서로 들어가고, 요청이나 사건에서 나온 업무는 자동 시작 대기열에 들어갑니다.
- 부서 이름이 이미 있으면 그 부서는 건너뜁니다. 이미 부서에 있는 담당자는 옮기지 않습니다.

## 요청하는 방법

- **회사에 요청**: 사이드바의 ‘회사에 요청’. ‘받을 곳’을 비워 두면 회사 접수 담당이 서비스를 가립니다. 서비스를 고르면 회사 접수를 건너뛰고 그 서비스 접수 담당에게 바로 갑니다(회사 접수 비용이 들지 않습니다).
- **서비스에 요청**: 서비스의 ‘요청’ 탭.
- 끝난 요청에는 ‘이어서 요청’이 있습니다. 앞 요청과 그 결과를 접수 담당에게 함께 넘깁니다.

## 접수 담당이 정하는 것

| 결과 | 화면에서 보이는 것 | 사람이 할 일 |
|---|---|---|
| 답변 | 요청 아래에 답이 붙고 ‘끝남’ | 없음 |
| 서비스로 넘김(회사) | 요청 아래에 서비스별 요청이 붙음. 모두 끝나면 회사 요청도 끝남 | 각 서비스 요청을 봅니다 |
| 업무 제안 | 업무 제안 카드(부서·담당자·완료 조건) | 검토 모드: 제목을 고쳐 ‘업무 등록’하거나 거절. 자동 모드: 바로 등록되고(‘자동 등록’), 실행 시작은 기존 자동 모드 규칙을 따릅니다 |
| 조치 제안 | 조치 카드와 이유 | 모드와 관계없이 승인해야 실행됩니다 |
| 질문 | 접수 담당의 질문과 답 칸 | 답하면 한 번 더 판단합니다. 두 번째도 되물으면 ‘직접 처리 필요’가 되어 사람이 업무를 만들거나 요청을 닫습니다 |
| 처리 불가 | 이유와 사람이 직접 할 수 있는 일 | 필요하면 다른 말로 다시 요청합니다 |

요청에서 등록한 업무의 ‘시작한 이유와 이어진 업무’에는 “사람의 요청으로 등록한 업무”와 요청 내용이 보입니다. 기다리는 질문·제안·조치·실패는 ‘내 할 일’의 ‘요청’ 칸에도 모이고, 새 할 일 알림 설정을 따릅니다.

## 회사 조치

| 조치 | 승인할 때 고르는 것 | 하는 일 |
|---|---|---|
| 코드 결과 전달 | 앱 저장소 서비스: 꺼낼 폴더(비어 있거나 없는 폴더, 비우면 기준 코드만 갱신)와 ‘작업 폴더로 쓰기’. 요청에 위치를 적었으면(예: “~/dev/workspace 하위에”) 접수 담당이 제안한 폴더가 미리 채워집니다(홈 폴더 안의 경로만). 작업 폴더가 있는 서비스: 결과 브랜치 또는 현재 브랜치에도 반영 | 아래 ‘코드 결과 전달’ |
| 결과 파일 저장 | 저장 위치 | 결과 하나를 파일로 저장 |
| 서비스 내보내기 | 저장 위치 | 키를 뺀 ZIP |
| 업무 흐름 실행 | 없음 | 확정된 버전을 실행(AI 비용이 듭니다) |

- 저장 창을 닫으면 아무것도 실행하지 않고 제안으로 남습니다.
- 같은 조치는 한 번만 실행됩니다. 실패하면 이유가 남고 다시 실행할 수 있습니다.
- 실행 중에 앱이 꺼지면 다시 켰을 때 ‘조치를 실행하는 동안 앱이 꺼졌습니다’로 남고, 저절로 다시 실행하지 않습니다. 결과를 보고 ‘끝난 것으로 확인’하거나 다시 실행합니다.

## 코드 결과 전달

성공한 실행 화면의 ‘코드 결과’에서 직접 할 수도 있고, 접수 담당이 조치로 제안하기도 합니다.

- **작업 폴더가 없는 서비스**(앱이 관리하는 저장소에서 작업): 전달하면 앱 저장소의 기준 코드가 실행의 최종 코드로 옮겨집니다. 폴더를 고르면 그 폴더에 저장소로 꺼내고(원격 연결 없음), ‘작업 폴더로 쓰기’를 켜 두면 서비스의 작업 폴더가 됩니다.
- **작업 폴더가 Git 저장소인 서비스**: `agent-office/result-<실행>` 브랜치를 만듭니다. ‘현재 브랜치에도 반영’은 작업 트리가 깨끗하고 빨리 감기가 될 때만 현재 브랜치를 옮기고, 아니면 이유를 남기고 브랜치만 만듭니다.
- 마지막 코드 단계가 여럿이면 합쳐서 전달합니다. 충돌이 나면 아무것도 바꾸지 않고 충돌 파일을 알려 줍니다.
- 코드를 바꾸지 않은 실행에는 ‘코드 결과’가 나타나지 않습니다.
- 접수 담당은 마지막 코드 결과가 아직 서비스 기준 코드에 없으면, 그 코드를 이어서 고치는 업무보다 코드 결과 전달을 먼저 제안합니다.

## 비용과 한도

| 항목 | 값 |
|---|---|
| 요청 하나의 판단 회차 | 2(질문에 답한 뒤 한 번 더) |
| 같은 회차의 자동 재시도 | 첫 호출 뒤 2회. 실패한 요청의 ‘다시 시도’마다 1회 더 |
| 판단 한 번의 항목 | 5개(서비스로 넘김·조치는 3개까지) |
| 접수 담당에게 넘기는 정보 | 40KB까지. 길면 결과 요약을 줄이고, 그래도 길면 자른 사실을 적습니다 |

- 접수 담당 배치와 ‘AI로 지침 다시 쓰기’도 AI 호출이라 같은 곳에 합산됩니다.
- 서비스 접수 담당의 호출(실패·재시도 포함)은 그 서비스 예산에 합산되고, 예산이 보류되면 요청도 ‘보류’로 기다립니다.
- 회사 접수 담당의 호출은 회사 접수 사용량으로 따로 셉니다. 월 예산을 정하면 이번 달 보고된 비용이 닿았을 때 회사 요청을 보류합니다. 비용을 알려 주지 않는 호출은 0원이 아니라 ‘비용을 알 수 없는 호출’로 셉니다.
- 접수 판단은 부서 판단·계획 생성과 별도로 한 번에 하나씩 처리합니다. 그래서 실행 밖 AI 호출은 동시에 최대 3건입니다.

## 알려진 제한

- 이미 확정한 업무 흐름 버전은 확정할 때의 작업 위치를 그대로 씁니다. 코드를 폴더로 꺼내 작업 폴더로 정한 뒤에도 그 버전을 다시 실행하면 앱 저장소에서 작업합니다(앱 저장소의 기준 코드도 전달한 코드로 갱신되므로 결과는 이어받습니다). 새 폴더에서 작업하게 하려면 버전을 다시 확정하세요. 새 업무의 작업 계획은 새 폴더를 씁니다.
- 접수 담당은 결과 파일 전체를 읽지 않습니다. 요약 필드나 문서 앞부분만 보므로, 결과 내용을 깊이 다루는 질문에는 업무를 제안합니다.
- 회사 요청은 서비스에 속하지 않아 서비스 사건 기록에 남지 않습니다.
- 앱에 들어 있는 ‘테스트 AI(가짜 응답)’ 연결은 정해진 형식으로 답하지 않으므로 접수 판단이 형식 오류로 실패합니다.
- Windows·Linux 화면은 따로 확인하지 않았습니다(CI의 자동 시험만).

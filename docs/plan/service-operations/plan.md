# Agent Office 개선 구현 계획서 — 사건과 산출물로 협업하는 작은 회사

작성일·수정일: 2026-10-22  
상태: 구현 중(6단계 완료), 6차 개정  
관련 파일: [진행 체크리스트](progress.md) · [현재/개선 후 업무 흐름](asis-tobe.html)

## 1. 목표와 설계 방향

**앱 안에서 작은 회사가 일하는 구조를 만든다.** 부서는 자기 책임을 맡고, 새로운 업무나 공유 자료를 보고 필요한 일을 제안한다. 다른 부서에 도움을 요청하거나, 다른 부서가 공개한 중간 결과를 활용해 별도 업무를 수행할 수 있다.

이 문서만으로 구현을 시작할 수 있어야 한다. 이전 대화나 기억을 전제로 하지 않는다. 체크박스는 실제 구현과 검증을 마친 뒤에만 완료로 표시한다. 저장 구조와 식별자는 [9장](#9-부록--데이터-구조와-식별자)을 기준으로 한다.

### 이전 계획에서 바꾸는 부분

이전 계획은 부서가 제안한 일을 미리 선택한 워크플로로 처리하는 데 집중했다. 이번 계획은 **부서 사이의 순서를 고정하지 않고, 업무와 공유 산출물에서 발생한 사건으로 협업을 연결한다.**

- 회사 전체: 사건을 보고 부서들이 필요한 협업을 제안하고 참여한다.
- 개별 작업: 담당자가 작은 작업 계획을 세워 실행한다. 기존 워크플로는 선택적으로 재사용한다.
- 업무 기록: 어떤 사건 때문에 일을 시작했고 어떤 자료를 사용했는지 남긴다.
- 전체 완료: 필요한 협업 결과가 모였는지 책임자가 확인한다.

이벤트 기반이라는 이유로 모든 부서를 항상 호출하거나 모든 사건에서 업무를 생성하지 않는다. 관심 있는 부서만 검토하고, 대응할 필요가 없으면 이유를 남기고 종료한다.

### 3차 개정에서 바뀐 부분

- 공유 자료는 기존 `artifacts` 테이블과 별도인 공유 문서·버전 구조로 저장한다. 기존 산출물은 출처로만 참조한다(4.4절).
- 부서의 AI 판단은 실행 엔진의 실행이 아니라 워크플로 AI 도우미와 같은 별도 작업으로 처리하고, 사용량을 서비스 예산에 합산한다(4.3절).
- 부서는 기존 역할·담당자 배정 위에 얹는 구조로 정의한다(4.1절).
- 사람이 한 명이라는 전제에서 수락·검토 단계를 줄인다(4.5절).
- 업무 실행 최소판을 공유 자료함보다 앞에 둔다(5장).
- 연쇄 깊이 기본값을 3으로 낮추고 사건당 판단 부서 수에 상한을 둔다(4.7절).

### 4차 개정에서 보완한 부분

- 직접 보낸 점검·협업 요청은 구독 여부와 관계없이 지정한 부서에 전달한다.
- 질문 답변에 따른 판단 회차와 실패한 공급자 호출의 재시도를 분리한다.
- 부서 판단과 실행 계획 생성이 같은 AI 작업·시도 기록을 사용하고, 실패·중단·재시도의 비용도 예산에 합산한다.
- 필수 협업 요청이 대기·질문·거절·취소 상태이면 수행 업무가 없어도 완료를 막는다.
- 파일 내용 버전과 확정 상태를 구분해 내용 변경 없이 초안을 확정할 수 있게 한다.

### 5차 개정에서 정한 부분

- 자동 모드의 참고용 협업 요청은 대표 담당자 AI가 수락·거절·질문을 결정한다. 이를 위해 AI 작업 종류 `collab_decision`을 추가한다(4.5절, 7단계).
- 실행 밖 AI 작업은 사용자 작업용과 백그라운드용 슬롯을 하나씩 둔다. 동시 호출은 최대 2건이다(4.3절).
- 확정 사건은 기본으로 알림만 만든다. 구독에서 직접 고른 부서만 판단을 받는다(4.4절).
- 계획 생성 요청 키, 자료 연결과 버전 고정 기록의 분리, 직접 요청의 판단 부서 상한 제외, 3단계 내부 순서를 정했다.

### 6차 개정에서 바꾼 부분

- 서비스 하나를 회사 하나로 본다. 부서는 회사 공통이 아니라 **서비스에 속한다.** 구성원은 그 서비스의 담당자(배정)다(4.1절).
- 회사 공통으로는 **부서 템플릿**을 둔다. 템플릿을 서비스로 가져오면 독립된 부서가 복사되어 만들어진다. 부서를 템플릿으로 저장할 수도 있다.
- 회사 부서를 서비스에 배정하던 ‘서비스 부서(`project_departments`)’는 없어지고 부서(`departments`)가 그 역할을 맡는다. 이전 판의 식별자 `project_department_id`·`projectDepartmentId`는 `department_id`·`departmentId`로 바꾼다.

### 대표 예시

1. 사용자가 ‘신규 고객 캠페인 준비’라는 공동 목표를 만들고 마케팅팀을 책임 부서로 지정한다.
2. 마케팅팀이 캠페인 기획안 초안을 공유한다. 캠페인 전체는 아직 완료되지 않았다.
3. 앱이 ‘캠페인 기획안 공유됨’이라는 사건을 기록한다.
4. 개발팀은 구현 검토가 필요한지 확인한다. 필요하면 ‘캠페인 페이지 구현 검토’ 업무를 제안한다.
5. 재무팀은 비용 확인이 필요한지 확인한다. 필요하면 ‘캠페인 예산 검토’ 업무를 제안한다.
6. 두 팀은 각자 업무를 수행한다. 두 업무의 순서를 미리 연결하지 않는다.
7. 마케팅팀은 각 팀이 공유한 결과를 받아 기획안을 수정한다.
8. 기획안이 새 버전으로 공개되면 그 버전을 사용한 팀에 재검토 후보가 전달된다.
9. 책임자가 필수 협업의 완료와 결과를 확인한 뒤 공동 목표를 완료한다.

다른 마케팅 업무가 개발팀만 필요로 하면 개발팀만 참여한다. 재무팀은 불필요한 일을 만들지 않는다. 관계없는 부서는 호출하지 않는다.

## 2. 현재 기반과 이번 범위

### 재사용할 기반

Agent Office는 Go·Wails·React·TypeScript·SQLite 기반 데스크톱 앱이다. 기존 서비스 프로젝트(`projects`), 역할(`roles`)·담당자 배정(`assignments`), 워크플로 실행, 승인·반려, 재작업, 검증, 예산, 기록 복구를 재사용한다.

현재 코드에는 다음 기반이 있다.

- 상태 변경과 사건을 같은 트랜잭션으로 저장한다(`storage.DB.Change`, `execution_events`). 사건에는 DB가 부여하는 전역 순서 번호가 있고 `run_id`는 비워둘 수 있다.
- 산출물(`artifacts`)에는 버전과 해시가 있으며 검증한 결과를 읽기 전용 사본으로 고정한다(`engine/verify.go`의 `freeze`).
- 질문·답변·전달·결정 메시지(`messages`)는 현재 실행 안의 협업을 지원한다.
- 워크플로 AI 도우미(`design/assist.go`, `workflow_assists`)는 실행 엔진을 거치지 않고 공급자를 직접 호출해 구조화된 결과를 받고, 사람이 수락할 때만 적용한다.
- 서비스에는 검토/자동 모드(`projects.mode`)와 자동 모드 허용 범위(`projects.auto_policy`)가 있다.
- 엔진 스케줄러는 `Wake()`와 2초 주기 틱으로 깨어나는 루프다.

현재 구조의 제약도 확인했다. 구현 방법은 이 제약에 맞춘다.

- 사건 구독 콜백(`DB.Subscribe`)은 커밋 직후 **DB 쓰기 잠금을 잡은 채** 호출되는 메모리 콜백이다. 콜백 안에서 DB에 쓰거나 AI를 호출하면 안 된다. 부서별 미처리 전달과 재시작 후 처리는 새로 만들어야 한다.
- `artifacts`는 `run_id`와 `step_attempt_id`가 필수이고, `version`은 같은 실행의 단계·출력 키별로 매긴다. 실행과 무관한 파일이나, 여러 실행에 걸친 같은 문서의 1판·2판을 표현할 수 없다.
- 실행(`runs`)은 확정된 워크플로 버전이 있어야 시작된다.
- 예산 집계(`engine/budget.go`의 `projectUsage`)는 `step_attempt_id`가 있는 `provider.usage` 사건만 합산한다. 워크플로 AI 도우미처럼 실행 밖에서 호출한 비용은 현재 예산에 잡히지 않는다.
- 기존 산출물 전달은 미리 정한 실행 그래프의 후속 단계가 중심이다.

### 이번 범위

- 부서 책임, 서비스별 배정, 사건 구독.
- 업무와 공동 목표, 부서 간 협업 요청·참여.
- 중간 산출물의 명시적인 공유와 버전 관리.
- 사건을 근거로 한 업무 제안과 검토·자동 실행.
- 사용자 요청과 정기 점검에 따른 업무 제안.
- 사건·자료·업무·결과를 따라갈 수 있는 운영 화면.

### 이번에 하지 않는 것

- 외부 고객 문의·매출·광고 시스템 자동 연결.
- 실제 게시·광고 집행·발송·실서비스 배포 연결.
- 앱 종료 후 상시 실행 서버와 원격 다중 사용자.
- Kafka 같은 외부 메시지 서버, 마이크로서비스 분리, 전체 데이터의 이벤트 소싱 전환.
- 서비스 사이의 자료 공유. 공유와 전달은 같은 서비스 안으로 한정한다.

단일 앱과 SQLite에서 먼저 검증한다. 사람은 기존 로컬 사용자 한 명(`local-owner`)이다. 기존 공급자 도구 권한과 예산 제한을 유지한다.

## 3. 알아야 할 개념

| 개념 | 쉬운 설명 | 예시 | 코드 이름 |
|---|---|---|---|
| 부서 | 한 서비스(회사) 안에서 계속 책임을 맡는 조직 | 캠페인 서비스의 마케팅팀, 개발팀, 재무팀 | `Department` |
| 부서 템플릿 | 여러 서비스에서 가져다 쓰는 회사 공통 부서 틀 | ‘개발팀’ 템플릿(책임, 추천 역할) | `DepartmentTemplate` |
| 업무 | 해결할 때까지 남는 일 | 캠페인 페이지 구현 검토 | `WorkItem` |
| 공동 목표 | 여러 업무를 묶는 상위 업무 | 신규 고객 캠페인 준비 | `WorkItem`(`kind='goal'`) |
| 사건 | 이미 일어난 사실을 기록한 것 | 기획안 공유됨, 협업 요청됨 | `execution_events`의 `work.*`·`document.*`·`department.*` |
| 전달 | 사건 하나를 부서 하나가 처리할 항목 | 기획안 공유됨 → 재무팀 판단 | `EventDelivery` |
| 구독 | 어떤 사건을 받아볼지 정한 설정 | 캠페인 기획안이 공유되면 개발팀이 확인 | `Subscription` |
| 판단 | 전달을 받은 부서 AI의 대응 결정 | 대응 불필요 / 업무 제안 / 추가 질문 | `Judgment` |
| 후속 제안 | 판단에서 나온 다음 일 | 개발 범위를 조사하자 | `WorkProposal` |
| 공유 문서 | 다른 업무에서도 사용할 수 있는 자료와 그 버전들 | 기획안 초안 1판, 예산 검토서 | `SharedDocument`, `SharedDocumentVersion` |
| 산출물 | 실행 한 단계가 만든 고정 결과(기존 기능) | 기획안 초안 작성 단계의 결과 파일 | `artifacts` |
| 실행 | AI나 사람이 작업한 한 번의 처리 기록(기존 기능) | 기획안 초안 작성 실행 | `runs` |

코드에서 ‘task’는 이미 사람이 맡는 단계(`InboxTask`)와 지침 계층 이름으로 쓰인다. 업무는 `work`/`WorkItem`으로 부르고 ‘task’를 쓰지 않는다.

공동 목표는 별도 회사 실행 그래프가 아니라 상위 업무로 표현한다. 각 부서는 자기 업무를 가지고 상위 업무에 연결한다. 다른 목표에서 같은 자료를 활용하는 경우에는 해당 목표에 업무를 만들고 원본 자료와 출처만 연결한다.

### 세 가지 참여 방식

- **요청받기:** 마케팅팀이 개발팀에 ‘구현 검토를 부탁한다’고 요청한다.
- **구독하고 제안하기:** 기획안 공유 사건을 받은 재무팀이 비용 검토를 제안한다.
- **자료를 찾아 활용하기:** 다른 부서가 공유 자료함에서 초안을 찾아 자기 업무의 입력으로 연결한다.

명시적 협업 요청은 받는 부서의 검토함에 전달한다. 일반 구독 사건은 대응 필요성을 먼저 판단한다. 단순 열람만으로 새 업무를 만들지 않는다.

## 4. 공통 동작과 기본값

### 4.1 부서와 업무

**부서와 기존 역할·담당자의 관계**

- 서비스 하나가 회사 하나다. 부서는 서비스에 속하고, 이름은 서비스 안에서만 겹치지 않으면 된다. 이름, 책임 문장, 대표 담당자, 구성원, 사용 여부와 나중에 붙을 구독·일정·자동화 규칙을 부서에 저장한다.
- 부서의 구성원은 같은 서비스의 담당자 배정(`assignments`)이다. 담당자는 서비스 안에서 최대 한 부서에 속한다. 다른 부서의 담당자를 구성원으로 넣으면 그 부서에서 옮겨지고, 옮겨진 담당자가 그 부서의 대표였다면 대표 지정도 풀린다. 역할은 기존처럼 회사 공통이다.
- 대표 담당자는 구성원 중 한 명이다. 부서의 AI 판단과 기본 업무 실행은 이 배정의 연결·모델·지침을 쓴다. 따로 AI 연결을 저장하지 않는다.
- 부서 책임 문장은 지침 계층에서 `project`와 `assignment` 사이에 `department` 층으로 넣는다. 순서는 회사 → 상위 역할 → 역할 → 프로젝트 → 부서 → 담당자 → 업무 → 재작업 피드백이다. 부서에 속하지 않았거나 부서가 ‘사용 안 함’이면 이 층이 없다.

**부서 템플릿**

- 템플릿은 회사 공통이다. 이름(회사 안에서 고유), 책임 문장, 추천 역할을 가진다.
- 서비스로 가져오면 템플릿의 이름·책임을 복사한 새 부서를 만든다. 추천 역할을 맡은 그 서비스의 담당자 중 아직 부서가 없는 사람이 구성원이 되고, 그중 첫 AI 담당자(없으면 첫 구성원)가 대표가 된다. 같은 이름의 부서가 있으면 이름 뒤에 번호를 붙인다.
- 가져온 부서는 원본 템플릿 ID만 기록한다. 템플릿을 고치거나 지워도 이미 가져온 부서는 바뀌지 않는다. 지우면 원본 연결만 끊긴다.
- 서비스의 부서를 템플릿으로 저장할 수 있다. 이름·책임과 구성원이 맡은 역할을 추천 역할로 복사한다.
- 화면에서는 버튼으로 가져오거나 템플릿 카드를 부서 목록에 끌어다 놓아 가져온다.

**업무**

- 업무에는 제목, 설명, 담당 부서·담당자, 완료 조건, 우선순위, 분류, 선택적 기한을 저장한다.
- 우선순위는 긴급·높음·보통·낮음(`urgent`/`high`/`normal`/`low`)이며 기본값은 보통이다.
- 업무 상태는 접수·준비·진행·대기·막힘·완료·취소(`received`/`ready`/`in_progress`/`waiting`/`blocked`/`done`/`cancelled`)다. 대기나 막힘에는 이유를 필수로 기록하고 화면에 표시한다.
- 업무 하나에 활성 실행(`running`/`waiting`/`paused`)은 하나만 허용한다. DB 부분 고유 색인으로 강제한다. 서로 다른 업무는 병렬로 실행할 수 있지만 기존 동시 실행 제한(`SetMaxActive`, 앱 전체·서비스별)을 그대로 따른다.
- 공동 목표의 결과 책임자는 부서 하나로 지정한다. 다른 부서의 참고용 참여가 공동 목표 완료를 막지 않는다.
- 업무 종료는 사람이 완료 조건을 확인한다. 실행 성공을 업무 전체 성공으로 간주하지 않는다.

### 4.2 업무 사건

초기 업무 사건은 다음으로 한정한다. AI의 토큰 출력이나 임의 파일 변경을 부서 사건으로 전파하지 않는다. 사건은 기존 `execution_events`에 `run_id` 없이 저장하고, 종류 이름의 접두어로 기존 실행 사건과 구분한다.

| 사건 | 종류 식별자 | 발생 시점 |
|---|---|---|
| 업무 등록됨 | `work.created` | 업무를 저장했을 때 |
| 협업 요청됨 | `work.collab_requested` | 특정 부서에 도움을 요청했을 때 |
| 산출물 공유됨 | `document.shared` | 공유 문서의 첫 버전을 공유했을 때 |
| 산출물 개정됨 | `document.revised` | 같은 공유 문서의 새 버전을 공유했을 때 |
| 산출물 확정됨 | `document.confirmed` | 사용자가 이미 공유된 버전의 내용을 확정했을 때 |
| 산출물 철회됨 | `document.withdrawn` | 공유 문서나 특정 버전을 철회했을 때 |
| 업무 완료됨 | `work.completed` | 사람이 업무를 완료했을 때 |
| 업무 재개됨 | `work.reopened` | 완료 업무를 다시 열었을 때 |
| 부서 점검 요청됨 | `department.check_requested` | 사용자가 제안을 요청하거나 정기 일정에 도달했을 때 |

사건 내용(`payload`)에는 사건이 속한 부서(업무·자료의 부서), 관련 업무·공동 목표, 분류, 원인 사건 번호, 연쇄의 최초 사건 번호와 깊이, 공유 문서 버전을 기록한다. 발생 시각과 서비스는 기존 열을 쓴다. 사건은 사실이며 곧바로 다른 부서에 대한 실행 명령이 되는 것은 아니다.

**지정한 부서에 직접 전달하는 사건**

- `department.check_requested`와 `work.collab_requested`에는 받는 부서인 `targetDepartmentId`를 필수로 기록한다. 발생 부서를 뜻하는 `departmentId`와 구분한다.
- 점검 요청은 대상 부서에 `purpose='judge'`, 협업 요청은 대상 부서에 `purpose='collab_request'` 전달을 만든다. 구독이 꺼져 있거나 분류가 일치하지 않아도 전달한다. 다른 부서에는 이 요청을 구독으로 재전파하지 않는다.
- 직접 전달도 같은 서비스인지, 부서가 활성 상태인지, 첨부 자료에 접근할 수 있는지 검사한다. 수동 요청에서 이 검사가 실패하면 사건을 만들기 전에 이유를 알린다. 자동 요청에서 실패하면 요청 원본에 보류 이유를 남긴다.
- 직접 전달은 구독 필터만 생략한다. 실제 AI 호출에는 예산·권한·연쇄 한도와 검토 정책을 그대로 적용한다.
- 일반 `work.*`·`document.*` 사건의 후속 참여는 구독 조건으로 결정한다. 자료 변경에 대한 필수 사용 영향 알림은 사용 기록을 기준으로 별도 `notify` 전달을 만든다.

프론트는 기존 `EventStored` 통지로 이 사건들도 받는다. 실행 화면은 모르는 종류의 사건을 무시해야 한다. 2단계에서 이 동작을 테스트한다.

### 4.3 부서의 관심 설정과 판단

**구독**

구독 화면에서는 사건 종류와 분류를 선택하고, 부서가 확인할 관점을 짧은 문장으로 적는다.

> 개발팀: ‘공유된 캠페인 기획안에 개발이 필요한 부분이 있는지 검토한다.’  
> 재무팀: ‘공유된 캠페인 기획안에 비용이나 예산 확인이 필요한지 검토한다.’

- 분류는 서비스별 고정 목록이다. 기본 목록은 기획·디자인·개발·비용·법무·운영·기타이고 서비스 설정에서 고칠 수 있다. 업무와 공유 문서는 분류를 0개 이상 가진다. 구독은 선택한 분류 중 하나라도 일치하면 해당한다. 분류를 비워 둔 구독은 모든 분류에 해당한다.
- 앱이 사건 종류·분류·서비스·자료 접근 범위로 먼저 거른 뒤 해당 부서 AI만 판단한다. 이 거르기는 결정적이며 AI를 호출하지 않는다.
- 사건 하나에서 구독으로 AI 판단을 받는 부서는 기본 최대 5개다. 넘치는 전달은 보류 상태로 두고 책임자에게 알린다. 사용자가 대상을 지정한 직접 요청(4.2절)은 이 상한에 포함하지 않는다.
- `document.confirmed`는 구독 화면에서 따로 선택한 경우에만 판단 대상이 된다. 사건 종류를 고를 때 기본으로 선택되지 않는다.

**판단 실행 방식**

- 판단은 실행 엔진의 실행으로 만들지 않는다. 워크플로 AI 도우미(`design/assist.go`)처럼 공급자를 직접 호출하되, 4.7절의 공통 AI 작업·시도 기록을 사용한다. 판단 결과는 `judgments`에 저장한다. 숨은 워크플로나 실행을 만들지 않으므로 기존 실행 슬롯을 사용하지 않는다.
- 실행 밖 AI 작업은 기존 실행 슬롯과 별도인 두 슬롯에서 처리한다. 각 슬롯은 앱 전체에서 한 번에 1건만 처리하므로 동시 호출은 최대 2건이다.
  - **사용자 작업 슬롯**(`lane='interactive'`): 사용자가 화면에서 직접 요청해 결과를 기다리는 작업. 실행 계획 생성, 사용자 점검 요청, 기존 자료 선택 검토의 판단.
  - **백그라운드 슬롯**(`lane='background'`): 사용자가 기다리지 않는 작업. 구독 사건의 판단, 정기 점검의 판단, 자동 모드의 협업 결정(`collab_decision`), 자동 모드의 계획 생성.
  - 각 슬롯은 작업 등록 순으로 처리한다. 같은 사건의 부서 간 순서는 전달 등록 순이다. 한 슬롯이 비어 있어도 다른 슬롯의 작업을 가져가지 않는다.
  - 한 호출의 제한 시간은 기존 AI 도우미와 같은 10분이다.
- 모든 공급자 호출과 재시도 전에 서비스 예산 보류 상태를 검사한다. 보류 중이면 AI 작업과 관련 전달을 `held`로 두고 호출하지 않는다. 예산 변경 시와 처리 루프의 주기 검사에서 다시 확인한다.
- 사용량은 각 공급자 호출 시도에 저장하고 `projectUsage`에 합산한다. 실패·중단·재시도와 계획 생성도 포함한다. 비용을 알 수 없는 시도는 기존과 같이 ‘알 수 없는 비용’으로 센다. 판단 행에는 비용을 다시 합산하지 않는다.
- 연결이 없거나 검증되지 않은 대표 담당자는 판단하지 않는다. 이 경우 전달을 실패로 남기고 이유를 표시한다.

**판단 결과**

- 판단 결과는 ‘대응 불필요’, ‘업무 제안’, ‘추가 질문’(`none`/`propose`/`question`) 중 하나다. 이유와 근거 자료도 기록한다. 형식에 맞지 않는 응답은 실패로 처리한다.
- 한 번의 판단으로 생성할 업무 제안은 최대 5개다.
- 같은 부서의 미해결 업무와 검토 중인 제안을 판단 입력으로 제공한다. 제목을 정규화해 일치하는 항목은 중복 후보로 표시한다. 이 표시는 참고용이며 등록을 막지 않는다.
- ‘추가 질문’은 사용자의 ‘내 할 일’에 질문 항목으로 들어간다. 첫 질문에 답하면 같은 전달에 대해 한 번 더 판단한다. 두 번째 판단도 질문이면 수동 검토 항목으로 바꾸고, 사용자가 직접 업무를 만들거나 대응 불필요로 닫는다.
- 첫 질문에 답하기 전에는 판단 작업과 전달을 `waiting_answer`로 둔다. 질문 대기 동안 슬롯을 점유하거나 공급자를 반복 호출하지 않는다. 답변 후에는 회차 1의 작업을 완료하고 회차 2의 새 판단 작업과 미처리 전달을 같은 트랜잭션에 준비한다. 실패 재시도는 같은 회차에서 처리한다.

**새 부서와 기존 자료**

- 새 부서는 서비스에 배정된 시점 이후의 사건을 받는다.
- 이전 자료는 사용자가 ‘기존 자료 검토’를 요청했을 때 현재 접근 가능한 자료만 대상으로 별도로 판단한다. 화면에는 기본 최근 50건을 보여주고 사용자가 선택한 자료만 판단한다. 과거 사건 전체를 재생하지 않는다.

### 4.4 공유 문서와 중간 결과

**저장 구조**

- 공유 문서는 기존 `artifacts`와 별도로 저장한다(`shared_documents`, `shared_document_versions`). 공유 문서는 같은 자료의 1판·2판을 묶는 단위이고, 버전 번호는 공유 문서 안에서 1부터 매긴다.
- 버전마다 고정 사본을 데이터 폴더 아래에 읽기 전용으로 저장한다. 경로·해시·크기를 기록하고, 기존 `freeze`와 같은 방식으로 복사 후 해시를 다시 확인한다.
- 버전의 출처는 ‘실행 산출물’ 또는 ‘작업 공간 파일’이다. 실행 산출물에서 공유하면 원본 `artifacts.id`를 출처로 기록한다. 작업 공간 파일에서 공유하면 서비스 작업 폴더 기준 상대 경로를 기록한다.
- 자료에는 제목, 분류, 작성 부서·업무, 초안/확정 표시, 버전, 해시와 출처를 남긴다.

**공유 규칙**

- 업무가 완료되기 전에도 초안을 공유할 수 있다. ‘업무 완료’와 ‘산출물 공유’는 별개다.
- 파일을 저장할 때마다 공유하지 않는다. 작성자가 공유하거나 허용된 자동 공유 규칙을 만족할 때만 고정본을 만든다.
- 내용 버전은 파일 내용이 바뀔 때만 만든다. 직전 버전과 해시가 같으면 새 내용 버전이나 공유·개정 사건을 만들지 않는다.
- 파일 구조 검증과 내용에 대한 업무적 승인은 구분한다. 공유한 초안은 승인된 자료가 아니다.
- 새 내용 버전은 항상 `stage='draft'`로 만든다. 사용자의 ‘이 버전 확정’ 동작은 같은 버전의 `stage`를 `final`로 바꾸고 확정자·확정 시각·메모를 기록한다. 파일·해시·버전 번호는 바꾸지 않는다. 내용의 고정과 검토 상태의 변경을 분리한다.
- 확정 상태 변경과 `document.confirmed` 사건을 같은 트랜잭션에 기록한다. 이미 확정된 버전의 재확정은 아무 변경도 하지 않고 사건도 중복 발행하지 않는다. 철회된 문서·버전은 확정할 수 없다.
- 새 내용 버전은 다시 초안이며 이전 버전의 확정을 물려받지 않는다. 확정자와 상태 변경 이력은 사건 기록으로 보존한다.
- 확정 사건은 기본으로 알림(`purpose='notify'`) 전달만 만든다. 대상은 그 버전을 연결·사용한 업무의 부서와 해당 사건 종류·분류를 구독한 부서다. AI를 호출하지 않으며 내용 개정 영향 확인이나 자동 재실행도 만들지 않는다. 구독에서 `document.confirmed`를 직접 선택한 부서만 판단(`judge`) 전달을 받는다.

**접근 범위**

- 공유 범위는 ‘서비스 전체’ 또는 ‘지정한 부서’ 둘 중 하나다. 기본값은 서비스 전체다.
- 다른 서비스에서는 보이지 않는다. 범위 밖 부서에는 전달·검색·참조를 허용하지 않는다.
- 작업 공간 파일 공유는 서비스 작업 폴더 안의 일반 파일만 허용한다. 심볼릭 링크와 폴더 밖 경로는 거절한다.

**사용과 개정**

- 다른 부서는 접근 가능한 자료를 검색해 자기 업무에 참조로 연결한다. 원본 파일을 공동 편집하지 않는다.
- 자료를 업무에 연결한 기록(`document_links`)과 실행이 실제로 사용한 버전의 고정 기록(`document_pins`)을 나눈다. 연결은 실행 전에도 만들 수 있고, 고정은 실행 시작 시 연결된 버전마다 만든다. 실행 입력에는 고정 사본을 넣는다. 새 버전이 나와도 진행 중인 입력을 몰래 교체하지 않는다.
- 새 버전 공유나 철회가 일어나면 이전 버전을 연결하거나 고정한 업무에만 영향 확인 항목을 만든다. 자동으로 재실행하지 않는다.
- 이전 버전과 결정은 보존한다. 이전 버전에 대한 검토 결과가 새 버전에도 유효하다고 간주하지 않는다.

**중간 결과를 만드는 방법**

첫 구현에서는 두 가지만 지원한다. 첫째, AI가 작은 실행 회차로 초안을 제출하면 그 결과를 공유하고 다음 회차에서 계속 작업한다. 상위 업무는 계속 진행 중이므로 중간 산출물을 활용할 수 있다. 둘째, 실행 도중에도 사용자가 작업 공간의 안정된 파일을 골라 고정본으로 공유할 수 있다. 복사 전후 해시나 수정 시각이 다르면 공유를 실패 처리하고 다시 시도하게 한다. 파일 변경을 계속 감시하는 기능이나 공급자가 지원하지 않는 중간 발행은 지원한다고 표시하지 않는다.

### 4.5 협업 관계와 완료

**협업 요청**

- 협업 업무는 원본 업무·사건·입력 자료와 연결하고 요청 부서와 수행 부서를 구분한다.
- 협업은 ‘참고용’ 또는 ‘완료에 필요한 업무’(`reference`/`required`)로 구분한다. 기본값은 참고용이다.
- 책임자는 검토해 필요한 협업을 필수로 지정한다. 필수 지정을 해제할 때는 이유를 남긴다.
- 받는 부서는 수락·추가 질문·거절할 수 있다. 거절이나 기한 초과를 자동 승인으로 처리하지 않는다.

**사람이 한 명일 때 누가 결정하는가**

- 앱의 사람은 사용자 한 명이다. 부서의 수락·거절은 사용자가 그 부서를 대신해 결정한다. 화면에는 ‘개발팀으로서 수락’처럼 어느 부서의 결정인지 표시한다.
- 자동 모드(4.6절)를 켜고 자동화 규칙에서 ‘참고용 협업 자동 결정’을 허용한 부서는 참고용 협업 요청을 대표 담당자 AI가 결정한다.
  - AI 작업 종류는 `collab_decision`이고 결과는 수락·거절·추가 질문(`accept`/`decline`/`question`) 중 하나다. 이유를 함께 기록한다.
  - 입력은 요청 질문, 원본 업무, 첨부 자료 버전, 받는 부서의 책임과 미해결 업무다.
  - 수락하면 받는 부서의 업무를 만들고 요청을 `accepted`로 바꾼다. 이 업무 생성은 자동 처리이므로 연쇄 깊이와 연쇄당 자동 업무 한도에 포함한다.
  - 거절은 이유와 함께 요청 부서에 알린다. 추가 질문은 판단의 질문과 같은 규칙(4.3절)으로 사용자에게 넘기고, 답변 후 한 번 더 결정한다.
  - 판단과 같은 회차·재시도·예산·슬롯 규칙(4.7절)을 따르고 백그라운드 슬롯을 쓴다.
  - 사용자는 AI의 결정을 확인하고 되돌릴 수 있다. 되돌리면 생성된 업무는 취소하고, 이유와 함께 기록을 남긴다.
- 필수 협업의 수락과 공동 목표 완료는 항상 사용자가 결정한다. 자동 결정이 허용되지 않은 부서의 참고용 요청도 사용자가 결정한다.
- 결정 횟수를 줄인다.
  - 제안을 수락하는 화면에서 업무 등록과 첫 실행 계획 확인을 한 번에 할 수 있다.
  - 같은 사건에서 나온 제안과 같은 공동 목표의 검토 항목은 ‘내 할 일’에서 묶어 보여주고 여러 건을 한 번에 수락·거절할 수 있다.
  - 사용자가 직접 보낸 협업 요청을 받는 부서가 수락하는 단계는 같은 화면에서 바로 처리한다.

**완료 규칙**

- 필수 협업 요청은 요청 상태가 `accepted`이고 연결된 수행 업무가 `done`일 때만 충족된다. 요청의 `requirement='required'`가 유지되는 한 `requested`·`question`·`declined`·`cancelled` 상태, 수행 업무가 없는 상태, 수행 업무가 미완료·재개·취소된 상태는 모두 미충족이다.
- 필수 요청이 미충족이면 원본 업무와 그 업무가 속한 공동 목표의 완료를 막고 요청·수행 업무·이유를 화면에 표시한다. 수행 업무가 생성된 요청만 조회해서 검사하면 안 된다. 상위 목표 완료는 하위 업무에 달린 필수 요청도 검사한다.
- 거절·취소·기한 초과만으로 필수 조건을 해제하지 않는다. 책임자가 이유를 남기고 참고용으로 전환하거나 대체 요청을 지정해야 한다. 대체 시에는 기존 필수 지정을 해제하고 새 필수 요청을 연결하는 변경을 같은 트랜잭션으로 기록한다. 새 요청이 충족되기 전에는 완료할 수 없다.
- 완료 조건 검사와 업무 완료 저장을 같은 트랜잭션에서 수행한다. 완료 이후 수행 업무가 다시 열리면 영향 확인을 만들고 책임자에게 알리며 완료된 목표를 몰래 다시 열지 않는다.
- 필수 의존 관계에 순환이 생기면 저장 전에 차단한다. 서로의 완료만 기다리는 상태를 만들지 않는다.
- 단순 자료 참조는 원본 업무의 완료 여부와 무관하게 가능하다. 초안을 참조했다는 사실은 계속 표시한다.

### 4.6 실행과 권한

**업무 실행**

- 회사 전체나 부서 전체의 고정 워크플로를 요구하지 않는다.
- 기본 실행 방식은 이렇다. 담당 AI가 지침·입력 자료·산출물·완료 기준을 가진 작은 작업 계획을 제안하고, 확정한 계획을 기존 엔진의 단일 단계 실행으로 처리한다.
- 작업 계획 생성은 `work_ai_jobs.kind='plan'`인 실행 밖의 AI 작업으로 저장한다. 3단계부터 4.7절의 동일한 대기열·예산 검사·시도별 비용 집계·시간 제한·복구 규칙을 적용한다. 계획을 다시 요청하거나 실패한 호출을 재시도해도 비용 기록을 생략하지 않는다.
- 화면은 계획 생성 버튼을 누를 때마다 요청 ID를 하나 만들어 보낸다. 작업의 `request_key`는 `plan:{work_item_id}:{요청 ID}`다. 같은 클릭이 두 번 전달되면 기존 작업을 돌려주고, 사용자가 다시 요청하면 새 작업을 만든다. 자동 모드의 계획 생성은 요청 ID 대신 원인 전달 ID를 쓴다.
- 계획의 입력과 결과를 해당 작업에 보관한다. 업무 내용·자료·완료 조건·담당자가 바뀌면 이전 입력 기준의 계획을 확정하지 못하게 하고 재생성을 요청한다. AI 계획 생성은 업무 실행을 시작하지 않으며 사용자가 직접 계획을 작성하는 경우에는 공급자를 호출하지 않는다.
- 엔진은 확정된 워크플로 버전이 있어야 실행하므로, 업무마다 전용 워크플로를 하나 만든다. 이 워크플로는 `workflows.work_item_id`로 업무에 연결하고 일반 워크플로 목록에는 보이지 않게 한다. 계획을 확정할 때마다 그 워크플로의 새 버전을 만들어 기존 버전 고정·실행·검증 체계를 그대로 쓴다.
- 반복 작업은 기존 워크플로를 선택해 업무에 연결할 수 있다. 필요한 협업은 사건과 별도 업무로 연결하며 실행 중인 그래프를 몰래 수정하지 않는다.
- 실행은 `runs.work_item_id`로 업무에 연결한다. 기존 실행 시작 API와 업무 없는 실행은 그대로 유지한다.

**검토 모드와 자동 모드**

- 검토 모드에서는 사람이 제안과 실행 계획을 확인한 뒤 시작한다.
- 자동 시작은 세 조건을 모두 만족해야 한다.
  1. 서비스가 자동 모드(`projects.mode='auto'`)다.
  2. 기존 허용 범위(`projects.auto_policy`)가 해당 연결을 허용한다.
  3. 부서의 자동화 규칙이 해당 업무 분류·허용 도구·작업 범위를 허용한다.
- 템플릿을 쓰는 경우 허용된 확정 버전인지도 검사한다.
- 개별 업무의 ‘시작 전 검토’를 우선한다. 허용 규칙에 맞지 않거나 자료·연결이 부족하면 검토함으로 보낸다.
- 실행 계획·완료 조건·자료·담당자가 바뀌면 이전의 시작 승인은 무효가 된다. 이미 실행 중인 계획의 권한은 넓히지 않는다.
- 자료 공유는 별도 허용 범위로 관리한다. 자동 실행 권한이 있다고 모든 초안을 자동 공유해도 된다는 뜻은 아니다.
- 기존 리뷰·도구 승인·예산·동시 실행 제한을 유지한다.
- 신규 부서는 검토 모드로 시작한다. 구독·정기 제안·자동 실행·자동 공유·참고용 협업 자동 결정은 모두 기본으로 꺼둔다.

### 4.7 중복·재시작·무한 후속 업무 방지

**저장과 전달**

- 상태 변경과 사건 저장은 기존 SQLite 트랜잭션(`DB.Change`) 안에서 함께 처리한다.
- 사건을 저장한 같은 트랜잭션에서 부서별 전달(`event_deliveries`)을 `pending`으로 만든다. 직접 요청은 4.2절의 지정 대상에 전달하고, 일반 후속 사건은 구독 조건으로, 사용 영향 알림은 자료 사용 기록으로 대상을 정한다.
- 전달 처리는 새 패키지 `internal/work`의 별도 처리 루프가 맡는다. 기존 구독 콜백은 이 루프의 채널에 신호만 보낸다(엔진 `Wake()`와 같은 방식). 콜백 안에서 DB에 쓰거나 AI를 호출하지 않는다. 신호를 놓쳐도 되도록 주기적인 틱도 둔다.
- 처리 루프는 `pending` 전달을 트랜잭션 안에서 `processing`으로 바꾼 뒤 처리한다. 앱 시작 시 관련 AI 작업과 시도의 상태를 먼저 복구한 뒤 미완료 전달만 다시 처리한다. 결과가 이미 저장된 판단이나 등록된 업무를 다시 생성하지 않는다.

**AI 작업, 판단 회차, 공급자 호출 시도**

- `work_ai_jobs`는 논리적인 요청 하나다. 종류는 실행 계획 생성(`plan`), 부서 판단(`judgment`), 협업 결정(`collab_decision`)이다. `work_ai_attempts`는 실제 공급자 호출 한 번이다. 이 구조는 3단계에 도입하고 5단계의 판단과 7단계의 협업 결정도 재사용한다.
- 부서 판단과 협업 결정의 논리 작업은 `(delivery_id, round)`별 하나다. 회차는 첫 결정 1과 질문 답변 후 결정 2만 허용한다. 실패·시간 초과·앱 중단은 회차를 늘리지 않는다.
- 공급자를 다시 호출할 때는 같은 작업 아래 새 시도 번호를 부여한다. 이전 실패·중단 시도와 보고된 사용량은 덮어쓰지 않는다. 같은 시도 안의 누적 사용량 보고는 최신 값으로 갱신하고, 서로 다른 시도의 사용량은 합산한다.
- 연결·예산 확인 후 호출 직전에 시도 행을 만든다. 호출 시작 여부나 최종 사용량이 불명확하면 비용을 0으로 확정하지 않는다. 신규 호출은 기존 보고 비용과 알 수 없는 비용 상태를 반영해 판단한다.
- 정상 응답은 시도의 완료, AI 작업의 결과, 판단 결과와 제안들, 관련 전달의 완료를 같은 트랜잭션에 저장한다. 첫 회차의 질문이면 작업과 전달을 `waiting_answer`로 둔다. 두 번째 회차의 질문이면 작업은 `ready`, 전달은 `done`으로 끝내고 질문을 수동 검토 항목으로 남긴다. 이미 저장된 결과는 재사용한다.
- 앱 시작 시 `working`으로 남은 시도는 `interrupted`로 끝낸다. 결과가 없는 작업만 `pending`으로 되돌리고, 관련 전달도 다시 처리할 수 있게 한다. 완료한 작업의 전달만 미완료로 남았다면 공급자를 다시 호출하지 않고 저장된 결과로 마무리한다.
- 하나의 논리 작업은 첫 호출과 최대 2회의 자동 재시도를 허용한다. 중단된 호출도 시도 횟수에 포함한다. 한도 후에는 실패 이유와 수동 재시도 버튼을 제공한다. 수동 재시도는 같은 작업·회차에서 새 시도 한 번을 만들며, 비용 이력은 유지하고 자동 재시도 한도를 초기화하지 않는다.
- 부서 판단·계획 생성의 시도 사용량은 3단계부터 서비스 예산에 합산한다. 실행 단계의 기존 `provider.usage` 집계와 중복 합산하지 않는다. 기존 워크플로 AI 도우미 자체의 비용 이력 이관은 이번 범위에 포함하지 않는다.

**중복 방지**

- 같은 사건·받는 부서·처리 목적에는 전달을 하나만 만든다. 고유 제약으로 강제한다.
- 판단·협업 결정과 그 AI 작업은 전달·회차별로 하나, 호출 시도는 작업·시도 번호별로 하나, 제안은 판단·순번별로 하나, 업무는 제안별로 하나만 만든다. 모두 고유 제약으로 강제한다.
- 사건 처리는 다시 시도될 수 있지만, 이미 만든 판단·제안·업무는 다시 만들지 않는다. 외부 조치가 정확히 한 번만 실행된다고 표현하지 않는다.

**연쇄 한도**

- 사람이 직접 한 행동에서 나온 사건은 깊이 0의 새 연쇄를 시작한다. 자동 처리(자동 등록 업무, 자동 공유, AI 협업 결정에 따른 업무 생성)에서 나온 사건은 원인 사건의 연쇄 시작 번호를 물려받고 깊이가 1 늘어난다. 시작 사건은 자기 번호를 내용에 적지 않고 비워 둔다(9.2절).
- 자동 후속 판단은 깊이 3까지만 한다. 연쇄 하나에서 자동 등록하는 업무는 기본 10개까지다. 사건 하나에서 판단할 부서는 기본 5개까지다(4.3절). 한도에 닿으면 새 자동 판단·등록을 보류하고 책임자에게 알린다. 한도 값은 서비스 설정에서 바꿀 수 있다.
- 같은 원인으로 반복해서 제안하지 않는다. 생성된 제안을 다시 제안 대상으로 삼지 않는다.
- 부서가 자기 사건에 반응하는 것은 기본으로 끈다. 단, 자기 업무가 사용한 자료가 바뀌었다는 알림은 별도 목적(`notify`)의 전달로 받을 수 있다.

**실패와 비용**

- AI 호출 실패는 위 시도 규칙으로만 재시도한다. 전달 실패와 AI 작업 실패에 각각 별도의 자동 재시도 루프를 두어 호출 수를 곱하지 않는다. 질문 대기와 예산 보류는 실패로 보지 않으며 반복 호출하지 않는다.
- 예산은 계획 생성·판단·각 재시도·실행 시작 전에 검사한다. 이미 진행 중인 엔진 실행들과 별도 AI 호출 때문에 한도를 넘을 수 있으므로 절대 상한을 보장하지 않는다. 사용량을 알 수 없는 공급자의 비용은 화면에 ‘알 수 없는 비용’으로 표시한다.

## 5. 단계별 구현 체크리스트

각 단계는 앞 단계에 의존한다. 단계 하나를 구현하고 검증한 뒤 다음 단계로 진행한다. 상세 완료 표시는 이 문서에, 검증 증거와 다음 작업은 progress.md에 기록한다. 마이그레이션은 단계별로 나누고 구현 시점의 다음 번호(현재 마지막은 `0007_assist_context.sql`)를 쓴다.

3단계까지 마치면 ‘업무를 만들고 실행해 결과를 확인한다’는 최소 흐름을 앱에서 볼 수 있다. 5단계까지 마치면 ‘공유 → 부서 판단 → 업무 → 실행’이 처음부터 끝까지 이어진다.

### 6단계 — 협업 요청과 공동 목표의 완료

**화면에서 보이는 변화:** 부서가 다른 부서에 도움을 요청하고, 필요한 결과를 기다릴 수 있다.

- [x] 협업 요청의 대상·질문·원본 업무·입력 자료를 저장한다.
- [x] 수락·추가 질문·거절과 받는 부서의 업무 생성을 구현한다. 화면에는 어느 부서로서 결정하는지 표시한다.
- [x] 참고용/필수 협업과 필수 지정·해제 이유를 기록한다.
- [x] 필수 업무가 미완료이거나 다시 열리면 공동 목표에 영향 확인을 표시한다.
- [x] 완료된 공동 목표를 몰래 다시 열지 않고 변경 검토를 요청한다.
- [x] 미완료 필수 협업이 있는 공동 목표의 완료와 필수 의존 순환을 차단한다.
- [x] 수행 업무가 없는 필수 요청도 검사한다. 대기·질문·거절·취소·기한 초과 상태의 필수 요청이 원본 업무와 공동 목표의 완료를 막는지 검증한다.
- [x] 필수 조건 해제·대체 이유를 저장하고, 완료 조건 검사와 완료 저장을 같은 트랜잭션에서 수행한다.
- [x] 협업 결과·정정·추가 질문을 원래 업무에서 찾아갈 수 있게 한다.

**완료 기준:** 마케팅이 개발과 재무에 따로 협업을 요청하고 두 팀이 병렬로 처리한다. 책임자는 필수 결과를 확인한 뒤 공동 목표를 완료한다.

구현 메모(6단계):
- 파일: 마이그레이션 `0014_collab_requests.sql`(`collab_requests`, `collab_request_history`), 저장소 `internal/storage/repo_collab.go`, 바인딩 `app_work.go`, 화면 `views/Collab.tsx`.
- 요청:
  - 요청하는 부서는 원본 업무의 담당 부서다. 담당 부서가 없거나 닫힌 업무, 같은 부서, 사용 안 함 부서, 받는 부서가 볼 수 없는 자료는 사건을 만들기 전에 거절한다.
  - `work.collab_requested`는 받는 부서에만 `collab_request` 전달을 만들고, 처리기는 기록만 한다. 결정은 요청에서 한다.
- 결정(사람이 부서를 대신함, `decided_by='user'`, 이력에 그 부서를 남김):
  - 수락: 받는 부서의 새 업무를 만들거나 그 부서의 열린 업무를 고른다. 새 업무는 요청 사건을 원인으로, 원본 업무의 열린 목표 아래에 두고, 함께 보낸 자료 판을 연결한다.
  - 질문: 요청하는 부서가 답하면 다시 결정을 기다린다.
  - 거절은 이유가 필요하다. 요청 취소는 수락 전에만 할 수 있다.
- 필수:
  - 요청 상태가 `accepted`이고 수행 업무가 `done`일 때만 충족이다. 원본 업무와 그 목표의 완료는 `setWorkStatusTx`가 같은 트랜잭션에서 검사해 막는다(목표는 하위 업무의 요청도 검사).
  - 해제는 이유가 필요하다. 대체는 한 트랜잭션에서 기존 요청을 참고용으로 바꾸고 새 필수 요청을 보낸다(`replaces_id`).
  - 순환은 기존 업무를 수행 업무로 고를 때와 수락된 요청을 필수로 바꿀 때 검사한다.
- 영향 확인(`required_reopened`, 대상은 요청 ID):
  - 필수 수행 업무가 완료에서 벗어나면(다시 열기·취소) 원본 업무와 목표에 만든다.
  - 완료된 목표 아래에 미충족 필수 요청이 생기면(필수 지정·새 요청·업무 이동) 그 목표에 만든다.
  - 업무·목표는 다시 열지 않는다. 같은 요청의 확인은 다시 연다.
- 화면:
  - 업무 상세의 ‘협업’: 요청 보내기, 받는 부서·요청하는 부서·책임자로서 결정하는 버튼, 완료를 막는 필수 협업 목록, 맡은 업무에서 요청한 업무로 이동, 이력.
  - 받은 일 화면의 ‘부서 간 협업’: 결정할 요청·답할 질문·거절된 필수 요청과 필수 영향 확인.

### 7단계 — 자동 모드와 기존 워크플로 연결

**화면에서 보이는 변화:** 허용한 작업은 자동으로 시작하고, 반복 작업에는 기존 워크플로를 쓴다.

- [ ] 업무에 기존 워크플로의 확정 버전을 선택해 연결하는 기능을 만든다.
- [ ] 부서의 자동화 규칙(분류·허용 도구·작업 범위·자동 공유·참고용 협업 자동 결정)을 저장하고 화면을 만든다.
- [ ] `collab_decision` AI 작업으로 참고용 협업 요청을 수락·거절·질문한다. 수락 시 업무 생성을 연쇄 한도에 포함하고, 필수 협업은 AI가 결정하지 않는다.
- [ ] 사용자가 AI의 협업 결정을 확인·되돌릴 수 있게 하고, 되돌린 기록과 이유를 남긴다.
- [ ] 4.6절의 세 조건을 모두 검사해 자동 시작하고, 맞지 않으면 검토함으로 보낸다.
- [ ] 사건으로 만들어진 부서 업무들이 서로 다른 실행으로 병렬 처리되게 한다.
- [ ] 계획·완료 조건·자료·담당자 변경 시 시작 승인을 무효로 한다.
- [ ] 예산·권한·연쇄 한도 보류를 검증한다.

**완료 기준:** 회사 전체의 고정 그래프 없이 개발과 재무가 자기 업무를 실행하고 중간 결과를 공유한다. 검토 모드는 기다리고, 자동 모드는 허용한 작업만 수행한다.

### 8단계 — 정기 제안과 새 부서의 참여

**화면에서 보이는 변화:** 부서가 요청을 받거나 정기적으로 새로운 일을 찾는다.

- [ ] 사용자 요청과 정기 제안을 함께 사용할 수 있게 한다.
- [ ] 매일·매주, 시각·요일과 저장 시점의 PC 시간대를 설정한다.
- [ ] 매 회차를 부서 점검 요청 사건으로 만들고 같은 판단 경로를 쓴다. 회차 키에 고유 제약을 둔다.
- [ ] 앱 종료 중 놓친 회차는 최신 한 회차만 처리한다.
- [ ] 일정 변경·비활성화·재시도에도 같은 회차의 제안을 중복 생성하지 않는다.
- [ ] 새 부서는 배정 후의 사건부터 받고, 이전 자료 검토는 별도 요청으로 시작한다.
- [ ] 보관된 서비스와 비활성 부서에서는 새 자동 처리를 시작하지 않는다.

**완료 기준:** 운영 도중 마케팅 부서를 새로 추가해 기존 자료를 검토시키고, 이후 사건과 정기 점검에 참여시킬 수 있다.

### 9단계 — 작은 회사 운영 화면과 인수 검증

**화면에서 보이는 변화:** 누가 왜 일하고 있고 어느 부서의 도움이 필요한지 한눈에 본다.

- [ ] 회사·서비스 화면에 부서별 업무와 검토·질문·막힘을 표시한다.
- [ ] 공동 목표에서 각 부서 업무, 필수 협업, 공유 자료와 결과를 조회한다.
- [ ] 업무에서 원인 사건·자료·다음 업무로 이동하는 연결을 제공한다.
- [ ] 기존 ‘내 할 일’에 제안·협업·질문·영향 확인·결과 검토를 구분하고, 공동 목표별로 묶어 표시한다.
- [ ] 사건 전달 실패·자동화 한도·예산 보류와 알 수 없는 비용을 표시한다.
- [ ] 실제 데이터가 없는 성과 수치는 만들지 않는다.
- [ ] 사용 안내, 알려진 제한과 아래 인수 증거를 기록한다.

**완료 기준:** 사용자에게 ‘어떤 사건 때문에 이 부서가 이 업무를 시작했는가’를 설명할 수 있고, 관련 업무와 결과를 화면에서 따라갈 수 있다.

## 6. 인터페이스와 데이터 변경

기존 Wails 바인딩과 프론트 API 방식에 다음 기능을 추가한다. 바인딩을 바꾸면 `frontend/wailsjs`를 다시 생성하고 기존 바인딩 테스트(`bindings_test.go` 등)를 갱신한다.

- 부서 템플릿·부서·구성원·책임·구독·분류·자동화 설정 관리.
- 업무·공동 목표·관계·실행 계획·상태·결정 관리.
- 사건·부서 전달·판단 결과·실패·보류 조회와 재시도.
- 공유 문서 공유·개정·철회·검색·참조·사용 영향 조회.
- 후속 제안·협업 요청·질문·수락·거절·일괄 처리.
- 사용자 점검 요청·정기 제안·운영 요약.

관련 저장 구조는 추가 마이그레이션으로 도입한다(9장). 기존 실행 시작 API와 업무 없는 워크플로 사용은 유지한다. 기존 실행은 같은 서비스의 업무 하나에 연결할 수 있다.

기존 산출물은 자동으로 공유 문서가 되지 않는다. 사용자가 공유하거나 명시된 자동 공유 규칙을 만족해야 한다. 기존 사건도 새 부서에 재생하지 않는다. 새 전달·참조·구독은 모두 서비스 범위와 자료 접근 범위를 검증한다.

## 7. 최종 인수 체크리스트

테스트용 서비스에 마케팅·개발·재무 부서를 설정하고 실제 외부 배포 없이 검증한다.

- [ ] 고정된 부서 간 그래프 없이 기획안 공유에서 개발·재무의 별도 업무가 생긴다.
- [ ] 다른 업무에서는 개발팀만 참여하고 재무팀은 대응 불필요로 남긴다.
- [ ] 사용자가 제안을 요청하는 방식과 정기 제안을 함께 사용할 수 있다.
- [ ] 명시적 도움 요청, 구독에 의한 참여, 자료 직접 활용이 모두 동작한다.
- [ ] 구독이 꺼져 있거나 분류가 달라도 직접 요청은 지정한 부서에만 전달된다. 자료 접근 제한과 예산 제한은 유지된다.
- [ ] 캠페인 완료 전에 초안을 공유하고 두 팀이 병렬로 작업할 수 있다.
- [ ] 원본이 바뀌어도 이미 사용한 입력 버전은 유지된다.
- [ ] 새 버전·철회는 그 자료를 사용한 업무에만 영향 확인을 요청한다.
- [ ] 초안 참조와 업무적 승인이 구분된다.
- [ ] 내용 변경 없이 같은 버전을 확정할 수 있고 해시·버전 번호는 유지된다. 확정 사건은 한 번만 발생하며 새 내용 버전은 다시 초안으로 시작한다.
- [ ] 확정 사건은 기본으로 알림만 만들고, 구독에서 직접 선택한 부서만 AI 판단을 받는다.
- [ ] 필수 협업과 참고용 협업의 완료 규칙이 다르며 순환 대기는 차단된다.
- [ ] 거절·취소·미수락으로 수행 업무가 없는 필수 요청도 완료를 막는다. 명시적으로 필수 조건을 해제하거나 대체한 기록이 남는다.
- [ ] 재시작·중복 전달·판단 후 종료·등록 후 종료에도 같은 업무가 중복 생성되지 않는다.
- [ ] 같은 회차에서 첫 호출 실패 후 재시도가 가능하고 질문 답변만 다음 회차를 만든다. `working` 시도를 남긴 재시작과 결과 저장 후 재시작을 각각 복구한다.
- [ ] 반응할 일이 없으면 불필요한 업무를 만들지 않는다.
- [ ] 연쇄 깊이·연쇄 업무 수·사건당 부서 수 한도에서 새 자동 처리가 보류된다.
- [ ] 판단·계획 생성의 성공·실패·중단·재시도 사용량이 서비스 예산에 합산된다. 같은 호출을 두 번 합산하지 않고 알 수 없는 비용을 0으로 표시하지 않는다.
- [ ] 예산 보류 중에는 새 판단·계획 생성·재시도·자동 실행이 시작되지 않는다.
- [ ] 검토 모드와 자동 모드가 기존 권한·예산을 준수한다.
- [ ] 사용자가 부서를 대신해 결정한 기록과 AI가 자동 결정한 기록이 구분된다.
- [ ] 자동 모드에서 AI가 참고용 협업을 수락·거절하고, 필수 협업은 사용자만 수락한다. 사용자가 AI 결정을 되돌릴 수 있다.
- [ ] 백그라운드 판단이 쌓여 있어도 사용자가 요청한 계획 생성은 사용자 작업 슬롯에서 바로 시작된다. 실행 밖 AI 호출은 동시에 2건을 넘지 않는다.
- [ ] 새 부서에 과거 사건이 모두 재전달되지 않는다.
- [ ] 서비스 두 개의 자료·사건·업무가 의도 없이 섞이지 않는다.
- [ ] 기존 역할·워크플로·실행·산출물을 업그레이드 후에도 사용할 수 있다.

각 단계에서 관련 Go·프론트 테스트를 실행한다. 전체 완료 시 저장소 루트에서 `go test ./...`, frontend 폴더에서 `npm test`, `npm run typecheck`, `npm run build`를 각각 실행하고 실제 앱을 확인한다.

시계와 AI 응답을 통제한 테스트(테스트 공급자)로 정기 실행·재시도·중복 방지를 검증한다. 테스트 공급자 결과와 실제 AI 결과를 구분한다. AI가 협업 필요성을 판단하는 품질은 전달 엔진의 신뢰성과 별도로 기록한다. 외부 연결이나 다른 OS를 시험하지 않았다면 미검증으로 남긴다.

저장소 규칙(0단계에서 확인):

- 별도 에이전트 지침 파일은 없다. `README.md`, `docs/environment.md`, `docs/decisions.md`, `.github/workflows/build.yml`을 지침으로 본다.
- 이 계획의 결정 중 명세 기본값을 바꾸거나 새로 확정한 것은 구현하면서 `docs/decisions.md`에 한 줄씩 기록한다.
- 단계(또는 단계 안의 큰 묶음)를 마치면 커밋한다. `main`에서 바로 작업하지 않고 기능 브랜치(`feat/...`)를 만든다. CI는 `main`과 `feat/**` 푸시에서 Windows·macOS·Ubuntu로 빌드·테스트한다.
- `main.go`가 `frontend/dist`를 포함하므로, 프론트를 바꾼 뒤 Go 테스트 전에 `npm run build`를 한다.
- Windows 개발 PC에는 cgo용 gcc가 없어 `-race` 없이 시험한다. CI는 race를 사용한다.
- 마이그레이션 규칙:
  - 파일 이름은 `NNNN_이름.sql`이다. 실행 시 남은 마이그레이션을 **한 트랜잭션**에서 차례로 적용하고, 하나라도 실패하면 모두 되돌린다.
  - 마이그레이션 중에도 외래 키 검사가 켜져 있다. `CHECK`·제약 변경처럼 테이블을 다시 만들어야 하면 `0005_diagram_artifacts.sql`의 방식(새 테이블 → 복사 → 삭제 → 이름 변경, 색인 재생성)을 따른다.
  - 기존 테이블에 열을 추가할 때는 `ALTER TABLE ... ADD COLUMN`에 기본값 `NULL`을 쓴다.
  - 앱보다 DB 스키마 번호가 높으면 열기를 거부한다. 이미 배포된 마이그레이션 파일은 고치지 않는다.
  - 마이그레이션을 추가할 때마다 `upgrade_test.go`에 ‘이전 번호의 DB에 데이터를 넣고 → 열어서 → 데이터·외래 키·색인이 유지되는지’ 확인하는 시험을 추가한다.
- 프론트는 모르는 사건 종류를 AI 활동 목록에서 건너뛴다(`AIActivity.tsx`). 다만 모든 사건이 서비스 화면 새로고침 신호를 올리므로(`live.tsx`), 업무 사건이 많아지면 새로고침 범위를 확인한다.

기존 코드의 시작점은 다음과 같다.

- `internal/storage/events.go`: 트랜잭션 사건 저장과 구독 콜백. 콜백 안에서 DB 쓰기나 AI 실행을 하지 않는다.
- `internal/storage/scope.go`: 서비스 범위 검사. 새 참조 종류를 여기에 추가한다.
- `internal/storage/migrations/`: 추가 마이그레이션 위치.
- `internal/engine/engine.go`: 스케줄러 루프와 `Wake()`. 전달 처리 루프는 같은 패턴으로 `internal/work`에 만든다.
- `internal/engine/verify.go`: 산출물 고정 저장(`freeze`). 공유 문서 고정 사본에 같은 방식을 쓴다.
- `internal/engine/budget.go`: 예산 집계. 실행 밖 AI 작업(계획 생성·판단·협업 결정)의 시도 사용량을 여기에 합산한다.
- `internal/engine/inbox.go`: ‘내 할 일’. 새 항목 종류를 추가한다.
- `internal/engine/messages.go`: 실행 안의 전달.
- `internal/design/assist.go`: 실행 엔진 밖의 AI 작업. 계획 생성·부서 판단·협업 결정의 선례다.

## 9. 부록 — 데이터 구조와 식별자

구현할 때 열 이름은 바꿀 수 있지만, 아래의 관계와 고유 제약은 유지한다. 서비스에 속한 행은 기존 스키마처럼 `(id, project_id)` 복합 키로 참조해 DB가 서비스 간 참조를 거부하게 한다. `ALTER TABLE ... ADD COLUMN`으로는 복합 외래 키를 추가할 수 없으므로, 기존 테이블에 추가하는 열(`work_item_id`)은 저장 시 코드에서 서비스 범위를 검사한다.

### 9.1 테이블

### 9.2 사건 내용

모든 `work.*`·`document.*`·`department.*` 사건의 내용에는 다음 필드를 넣는다.

```json
{
  "departmentId": "사건이 속한 부서(업무·자료의 부서). 이 부서는 자기 사건을 판단하지 않는다",
  "targetDepartmentId": "점검·협업 직접 요청의 받는 부서, 이 두 종류에 필수",
  "collabRequestId": "협업 요청 사건일 때의 요청 ID",
  "workItemId": "관련 업무",
  "title": "전달함에 보일 제목(업무 제목 등)",
  "note": "사람이 남긴 이유나 요청 내용",
  "goalId": "관련 공동 목표",
  "categories": ["개발"],
  "causeSequence": null,
  "chainRootSequence": null,
  "chainDepth": 0,
  "automated": false,
  "documentVersionId": "document.* 사건만"
}
```

`automated`가 `false`이면 새 연쇄를 시작한다. 이때 `chainRootSequence`는 비워 두고(`null`) `chainDepth`는 0이다. `Change.Emit`은 사건 내용을 만든 뒤 저장해 순서 번호를 받으므로, 시작 사건은 자기 번호를 내용에 적을 수 없기 때문이다. `causeSequence`도 원인이 없으면 비워 둔다.

`true`이면 원인 사건의 연쇄를 잇는다. `chainRootSequence`는 원인 사건의 `chainRootSequence`이고, 그것이 비어 있으면 원인 사건 자신의 순서 번호다. `chainDepth`는 원인 사건의 깊이에 1을 더한다.

사건의 연쇄 시작 번호는 항상 “`chainRootSequence`가 있으면 그 값, 없으면 그 사건의 `sequence`”로 읽는다. SQL에서는 `COALESCE(json_extract(payload, '$.chainRootSequence'), sequence)`로 계산한다. 이 계산은 한 곳의 함수로 모아 두고, 연쇄당 자동 등록 업무 수를 셀 때도 같은 식을 쓴다. 조회가 느려지면 같은 식에 표현식 색인을 추가한다.

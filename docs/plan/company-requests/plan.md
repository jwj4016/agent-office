# Agent Office 개선 구현 계획서 — 회사에 요청하면 접수 담당이 처리한다

작성일·수정일: 2026-10-30  
상태: 구현 완료, 3차 개정(접수 담당 자동 배치) 반영  
관련 파일: [진행 기록](progress.md) · [서비스 운영 계획](../service-operations/plan.md)

## 1. 목표와 설계 방향

**사람은 회사에 말로 요청하고, 회사 안의 접수 담당이 그 요청을 받아 알맞게 처리한다.** 사람이 부서를 골라 업무를 만들거나, 결과 코드를 git으로 직접 꺼내는 일을 하지 않아도 되게 한다.

이 문서만으로 구현을 시작할 수 있어야 한다. 이전 대화나 기억을 전제로 하지 않는다. 체크박스는 실제 구현과 검증을 마친 뒤에만 완료로 표시한다. 저장 구조와 식별자는 [9장](#9-부록--데이터-구조와-식별자)을 기준으로 한다.

- 접수 담당은 **회사 전체에 하나, 서비스마다 하나**씩 둔다. 회사 접수는 요청이 어느 서비스의 일인지 가려 서비스 접수로 넘기고, 서비스 접수는 그 서비스 안에서 처리 방법을 정한다.
- 접수 담당은 직접 일을 하지 않는다. 바로 답하거나, 업무로 만들거나, 앱이 실행할 **회사 조치**를 제안하거나, 되묻는다.
- 앱 밖(사용자 폴더·사용자 저장소)에 쓰거나 비용이 드는 조치는 AI가 하지 않는다. 접수 담당이 제안하고, 사람이 ‘내 할 일’에서 승인하면 앱이 실행한다.
- 실행이 만든 코드를 사람에게 넘기는 **코드 결과 전달**을 새로 만든다. 지금은 코드가 실행의 작업 브랜치에만 남아 사람이 쓸 수도, 다음 실행이 이어받을 수도 없다.

### 2차 개정(구현하며 바꾼 부분)

- 요청의 AI 호출은 `work_ai_jobs`를 다시 만들지 않고 요청 전용 테이블(`requests`·`request_attempts`·`request_items`)에 기록한다. `work_ai_jobs`는 판단·협업·자동 시작 테이블이 참조해 다시 만들기가 위험하고, 서비스 없는 회사 요청도 같은 구조로 다룰 수 있다. 요청 자체가 작업이다(`received` → `triaging`). 그래서 마이그레이션은 새 테이블과 열 하나만 더한다(`0017_requests.sql`).
- 접수 판단은 부서 판단·계획 생성의 두 슬롯과 별도로 한 번에 하나씩 처리한다. 실행 밖 AI 호출은 동시에 최대 3건이다.
- 코드 전달 기록은 테이블 대신 실행 사건(`code.delivered`·`code.delivery_failed`)으로 남긴다.
- 서비스 접수 담당을 사람으로 바꾸면 지정을 지우지 않고, 접수할 때 검사해 ‘접수 담당 필요’로 기다린다(담당자 삭제 기능은 없다).
- 이미 확정한 업무 흐름 버전은 확정할 때의 작업 위치를 그대로 쓴다(버전 스냅숏). 전달 뒤 그 버전을 다시 실행하면 앱 저장소에서 작업하되, 기준 코드가 전달한 코드로 갱신되어 결과를 이어받는다.

### 3차 개정(접수 담당 자동 배치, 2026-10-31)

사장님 요청: 요청을 처리할 접수 담당이 없으면 AI가 서비스를 분석해 알맞은 담당자를 새로 만든다. 직접 새로 만들기와 기존 인원 중 지정도 둔다.

- 접수 담당 없이 요청이 오면 실행기가 AI에게 서비스(목표·지침·부서·담당자·최근 실행)를 보여 주고 접수 담당의 **이름과 서비스 전용 지침**을 쓰게 한다. 앱은 그것으로 새 AI 담당자를 만들고 접수 담당으로 정한 뒤 같은 요청을 이어서 판단한다. 회사 접수 담당도 같은 방식이다(회사 지침과 서비스 목록을 보여 줌).
- 담당자는 회사 공통 역할 **‘접수 담당’ 하나**에 배정한다(처음 한 번 만든다). 서비스마다 다른 점은 담당자 지침에 넣는다. 역할은 서비스가 공유하고 부서만 서비스마다 복사본이라는 지금 구조를 따른다.
- AI 연결은 AI가 고르지 않는다. 그 서비스의 AI 담당자가 가장 많이 쓰는 검증된 연결(없으면 회사 전체에서 가장 많이 쓰는 연결)과 그 연결에서 가장 많이 쓰는 모델을 앱이 정한다. 검증된 연결이 없으면 ‘접수 담당 필요’로 기다린다.
- 요청 하나가 일으키는 자동 배치는 2번까지다. 실패하면 이유와 함께 사람을 기다린다. ‘사용 안 함’으로 둔 접수 담당, 사람으로 바뀐 담당자는 자동으로 바꾸지 않는다.
- 배치·지침 쓰기 호출은 `desk_staffing`에 기록하고(마이그레이션 `0018_desk_staffing.sql`), 서비스 예산 또는 회사 접수 사용량에 합산한다.
- 부서·담당자 화면의 접수 담당은 세 가지 방법을 둔다: AI에게 맡기기, 새로 만들기(이름·연결·모델·지침), 기존 인원 중 지정. 정해진 접수 담당에는 ‘AI로 지침 다시 쓰기’가 있다. 요청 카드에는 “AI가 ‘…’를 새로 배치했습니다”가 보인다.
- 사장님이 요청에 꺼낼 위치를 적으면(예: “~/dev/workspace 하위에”) 접수 담당이 `deliver_code`에 폴더를 **제안**하고 승인 화면에 미리 채운다. 홈 폴더 안의 경로만 받는다. 실행은 여전히 사람 승인 뒤에만 한다.

### 대표 예시

1. 사용자가 회사 요청 칸에 “빌라노트 코드 내 폴더로 보내 줘”라고 쓴다.
2. 회사 접수 담당이 빌라노트의 일이라고 판단해 빌라노트 접수로 넘긴다.
3. 빌라노트 접수 담당이 실행 ‘빌라노트 MVP’(성공)의 코드 결과를 보고 ‘코드 결과 전달’ 조치를 제안한다.
4. ‘내 할 일’에 “빌라노트 MVP 코드를 전달할까요?”가 뜬다. 사용자가 폴더(`~/dev/villanote`)를 고르고 승인한다.
5. 앱이 최종 코드를 서비스 기준 코드로 반영하고, 그 폴더에 저장소로 꺼낸 뒤 서비스의 작업 폴더로 등록한다.
6. 사용자가 이어서 빌라노트 접수에 “QA·전문가 검토에서 나온 문제 고쳐 줘”라고 쓰면, 접수 담당이 업무 3개를 제안한다. 사용자가 등록하면 그 업무들은 방금 전달된 코드에서 시작한다.

## 2. 현재 기반과 이번 범위

### 재사용할 기반

- 실행 밖 AI 작업(`work_ai_jobs`·`work_ai_attempts`, `internal/work/ai.go`): 사용자 작업·백그라운드 두 슬롯, 시도별 사용량과 서비스 예산 합산, 재시작 복구, 자동 재시도 2회. 종류별 `Kind`(`Prepare`·`Accept`·`Complete`)만 추가하면 된다.
- 구조화 호출(`design.RunJSONCall`): 지시·입력·JSON 스키마로 한 번 호출하고 결과를 검사한다. 파일을 읽거나 명령을 실행하지 않는다.
- 부서 판단의 결과 구조(대응 불필요·업무 제안·추가 질문)와 질문 2회차 규칙(`internal/work/judge.go`).
- 업무·제안 등록, 업무 원인 표시(`WorkLineage`), 자동 모드 규칙(`auto_starts`), ‘내 할 일’(`PendingDecisions`)과 새 할 일 알림.
- 결과 파일 저장(`SaveArtifactAs`), 서비스 내보내기(`ExportProject`), 실행 시작(`StartRun`).
- Git 도우미(`internal/workspace/git.go`): `Init`·`Head`·`Dirty`·`AddWorktree`·`Merge`·`IsAncestor` 등.

### 확인한 제약

- `work_ai_jobs`·`work_ai_attempts`·`execution_events`는 모두 `project_id`가 필수다. 서비스가 없는 회사 접수는 지금 구조에 기록할 곳이 없다.
- `work_ai_jobs.kind`는 CHECK로 `plan`/`judgment`/`collab_decision`만 허용하고, 판단 종류는 전달(`delivery_id`)이 필수다. 새 종류를 넣으려면 테이블을 다시 만들어야 한다.
- 부서는 서비스에 속하고, 담당자 배정(`assignments`)도 서비스에 속한다. 회사 단위의 AI 담당자는 없다. 실제 데이터의 서비스 3개에는 부서가 하나도 없다.
- 작업 폴더가 없는 서비스는 앱이 관리하는 저장소(`projects/<서비스>/repo`)에서 실행한다. 실행은 그 저장소의 `HEAD`에서 시작하고, 코드 단계의 결과는 `agent-office/<실행>/<단계>-g<세대>-a<시도>` 브랜치에만 커밋된다. **`master`는 갱신되지 않으므로 다음 실행이 이전 결과를 이어받지 못한다.**
- 작업 폴더가 Git 저장소인 서비스는 결과 브랜치가 사용자 저장소에 생긴다. 앱은 사용자의 작업 트리를 건드리지 않는다(`internal/engine/workspaces.go` 18행 주석).
- 실행 하나에 코드 단계가 여럿이면, 뒤 단계가 앞 단계 커밋을 합쳐 시작한다. 그래도 서로 이어지지 않은 마지막 단계가 둘 이상일 수 있다.

### 이번 범위

- 회사·서비스 접수 담당 설정과 요청 창구.
- 접수 판단: 답변·업무 제안·회사 조치 제안·추가 질문·처리 불가.
- 회사 접수에서 서비스 접수로 넘기기.
- 코드 결과 전달: 서비스 기준 코드 갱신, 폴더로 꺼내기, 사용자 저장소에 결과 브랜치 만들기.
- 회사 조치 목록과 사람 승인.
- 빌라노트 실제 데이터로 전체 확인.

### 이번에 하지 않는 것

- 검토 단계의 ‘고쳐야 함’을 앞 단계로 되돌리는 흐름 동작. 빌라노트 1차 실행에서 드러났지만 별도 과제로 둔다.
- 접수 담당이 파일을 읽거나 명령을 실행하는 것. 접수 판단에 필요한 정보는 앱이 요약해 넣는다(4.3절).
- 외부 배포, 원격 저장소 push, 다른 사람에게 보내는 일.
- 음성·메신저 등 앱 밖에서 들어오는 요청.

## 3. 알아야 할 개념

| 개념 | 쉬운 설명 | 예시 | 코드 이름 |
|---|---|---|---|
| 접수 담당 | 요청을 받아 처리 방법을 정하는 AI | 회사 비서실, 빌라노트 접수 | `IntakeDesk` |
| 요청 | 사람이 회사나 서비스에 말로 맡긴 일 | “빌라노트 코드 내 폴더로 보내 줘” | `Request` |
| 접수 판단 | 접수 담당이 요청을 보고 정한 처리 방법 | 서비스로 넘김, 업무 제안, 조치 제안 | `work_ai_jobs.kind='intake'` |
| 처리 항목 | 판단에서 나온 개별 할 일(업무 제안·조치 제안·넘김) | ‘전문가 검토 기준 공백 고치기’ 업무 | `RequestItem` |
| 회사 조치 | 앱이 정해진 방식으로 실행하는 일. 사람 승인 필요 | 코드 결과 전달, 결과 파일 저장 | `RequestItem.kind='action'` |
| 최종 코드 | 성공한 실행의 코드 단계들을 모두 합친 커밋 | 빌라노트 MVP의 `11097fd` | `FinalCode` |
| 서비스 기준 코드 | 다음 실행이 시작하는 커밋 | 앱 저장소의 `master`, 또는 작업 폴더의 현재 커밋 | — |

‘요청’은 이미 협업 요청(`collab_requests`)과 도구 승인 요청에서 쓰는 말이다. 화면에서는 ‘회사에 요청’·‘서비스에 요청’으로, 코드에서는 `Request`와 `requests` 테이블로 구분하고 협업 요청 코드와 이름을 섞지 않는다.

## 4. 공통 동작과 기본값

### 4.1 접수 담당

**회사 접수 담당**

- 회사(조직)마다 하나다. 이름(기본 ‘비서실’), AI 연결, 모델, 지침, 사용 여부, 선택적인 월 예산을 저장한다.
- 회사에는 담당자 배정이 없으므로 연결과 모델을 접수 담당 설정에 직접 저장한다. 회사 지침(`organizations.instructions`)은 접수 지시에 함께 넣는다.
- 회사 설정 화면(`Organization.tsx`)에서 지정한다. 지정하지 않았거나 연결이 검증되지 않았으면 회사 요청 칸에 이유와 설정 버튼을 보여 주고, 서비스를 직접 골라 요청하는 것만 허용한다.

**서비스 접수 담당**

- 서비스마다 하나다. 그 서비스의 AI 담당자(배정) 한 명을 고른다. 연결·모델·지침은 그 배정의 것을 쓰고, 접수 담당 설정에는 추가 지침만 둔다.
- 서비스의 부서·담당자 화면(`Team.tsx`)에서 지정한다. 부서가 없어도 지정할 수 있다.
- 지정하지 않은 서비스로 요청이 오면 요청을 ‘접수 담당 필요’로 두고 ‘내 할 일’에 지정 항목을 만든다. 지정하면 그 요청부터 이어서 처리한다.
- 배정을 지우거나 사람 담당자로 바꾸면 지정이 풀린다. 지정이 풀린 동안 들어온 요청은 위와 같이 기다린다.

### 4.2 요청

- 요청에는 본문, 받는 곳(회사 또는 서비스), 상위 요청(회사 요청에서 넘어온 경우), 이어서 한 요청(앞 요청), 상태를 저장한다. 요청자는 기존 로컬 사용자(`local-owner`)다.
- 회사 요청 칸에서 서비스를 직접 고르면 회사 접수를 건너뛰고 그 서비스 접수로 바로 보낸다. 회사 접수 비용이 들지 않는다.
- 상태는 다음과 같다.

| 상태 | 뜻 |
|---|---|
| `received` | 저장됨. 접수 담당이 아직 보지 않음 |
| `waiting_desk` | 서비스 접수 담당이 없어 기다림 |
| `triaging` | 접수 판단 중 |
| `question` | 접수 담당이 되물어 사람의 답을 기다림 |
| `proposed` | 사람이 결정할 처리 항목이 남음 |
| `routed` | 회사 접수가 서비스로 넘김. 하위 요청이 끝나면 함께 끝남 |
| `in_progress` | 처리 항목이 모두 결정됐고, 승인된 조치가 실행 중 |
| `done` | 답변을 했거나 모든 처리 항목이 끝남 |
| `declined` | 접수 담당이 처리할 수 없다고 판단함(이유 필수) |
| `cancelled` | 사람이 취소함 |
| `failed` | 접수 판단이 재시도 한도까지 실패함(이유 필수) |

- 요청에서 만든 업무가 완료돼야 요청이 끝나는 것은 아니다. 업무를 등록하면 그 처리 항목은 끝난다. 업무 진행은 업무 화면에서 보고, 요청 상세는 그 업무로 가는 연결을 보여 준다.
- ‘이어서 요청’은 앞 요청을 참조하는 새 요청이다. 접수 판단 입력에 앞 요청의 본문과 결과를 넣는다.
- 요청 취소는 아직 결정하지 않은 처리 항목과 대기 중인 접수 판단만 취소한다. 이미 등록한 업무나 실행된 조치는 되돌리지 않는다.

### 4.3 접수 판단

**실행 방식**

- 접수 판단은 `work_ai_jobs`의 새 종류 `intake`다. 사람이 기다리는 일이므로 사용자 작업 슬롯(`interactive`)에서 처리한다. 재시도·복구·사용량 규칙은 기존 AI 작업과 같다.
- 요청 하나에 판단 회차는 최대 2회다. 1회차에서 되물으면 요청은 `question`, 사람이 답하면 2회차를 만든다. 2회차도 되물으면 처리 항목 없이 ‘사람이 직접 처리’로 바꾸고, 사람이 업무를 만들거나 요청을 닫는다. 판단의 `request_key`는 `intake:{request_id}:{회차}`다.
- 서비스 접수의 비용은 그 서비스 예산에 합산하고, 예산 보류 중에는 호출하지 않는다.
- 회사 접수의 비용은 서비스가 없으므로 회사 접수 사용량으로 따로 센다(9.1절). 월 예산을 정했으면 넘었을 때 새 판단을 보류하고 이유를 보여 준다. 비용을 알 수 없는 호출은 0원이 아니라 ‘알 수 없는 비용’으로 센다.

**판단 입력**

앱이 판단 입력을 만들고, 접수 담당은 그 밖의 파일을 읽지 않는다. 입력 전체는 기본 40KB를 넘지 않게 자른다. 잘랐다는 사실도 입력에 적는다.

- 회사 접수: 회사 지침, 사용 중인 서비스 목록(ID, 이름, 목표 앞부분, 접수 담당 유무, 부서 이름), 앞 요청.
- 서비스 접수:
  - 서비스 목표·지침의 앞부분, 작업 폴더 유무와 서비스 기준 코드(4.6절)
  - 부서(책임 문장·대표)와 담당자(역할·AI/사람)
  - 진행 중인 업무 최근 20건(제목·상태·부서)
  - 최근 실행 10건(흐름 제목·상태·끝난 시각, 코드 결과가 있으면 최종 코드 계산 가능 여부와 전달 여부)
  - 최근 결과 30건(출력 키·형식·단계 제목·크기, `summary`·`ceo_summary`가 있으면 그 앞 1,000자, 마크다운이면 앞 1,000자)
  - 지금 쓸 수 있는 회사 조치 목록(4.5절)과 각 조치에 넣을 수 있는 ID
  - 앞 요청

**판단 결과**

결과 종류는 하나이고, 종류에 맞는 처리 항목을 함께 낸다. 형식이 맞지 않거나 입력에 없는 ID를 쓰면 그 시도를 실패로 처리한다.

| 종류 | 회사 접수 | 서비스 접수 | 처리 항목 |
|---|---|---|---|
| `answer` | 가능 | 가능 | 없음. 답변을 요청에 저장하고 `done` |
| `route` | 가능 | — | 서비스별 넘김 최대 3개(서비스 ID, 그 서비스에 맞게 고친 요청문) |
| `work` | — | 가능 | 업무 제안 최대 5개(제목·설명·완료 조건·분류·우선순위, 선택: 부서·담당자·공동 목표) |
| `action` | — | 가능 | 회사 조치 제안 최대 3개(조치 종류와 매개변수, 이유) |
| `question` | 가능 | 가능 | 없음. 질문을 저장하고 `question` |
| `decline` | 가능 | 가능 | 없음. 이유와 사람이 할 수 있는 일을 저장하고 `declined` |

- 서비스 접수가 업무와 조치를 함께 제안해야 할 때는 `action`을 쓰고, 업무는 처리 항목에 함께 넣는다(조치 다음에 할 일). 한 판단의 처리 항목은 모두 합쳐 최대 5개다.
- 답변은 판단 입력에 있는 정보로만 한다. 입력에 없는 내용을 물으면 그 내용을 볼 수 있는 업무를 제안하거나 `decline`으로 이유를 남긴다. 이 원칙을 지시에 적는다.

### 4.4 업무로 넘기기

- 회사 접수의 `route`는 서비스마다 하위 요청을 만든다. 이 넘김은 앱 안의 일이라 사람 승인 없이 바로 한다. 상위 요청은 `routed`가 되고, 하위 요청이 모두 끝나면(`done`·`declined`·`cancelled`) `done`이 된다.
- 서비스 접수의 업무 제안은 서비스 모드를 따른다.
  - 검토 모드: ‘내 할 일’에 업무 제안으로 올린다. 사람이 등록·수정 후 등록·거절한다.
  - 자동 모드: 바로 업무로 등록한다. 실행 시작은 기존 자동 모드 규칙(`auto_starts`, 서비스 허용 연결·부서 자동화 규칙·예산)을 그대로 따른다. 규칙에 맞지 않으면 ‘검토 필요’로 넘어간다.
- 요청에서 만든 업무에는 원인 요청을 기록한다. 업무 상세의 ‘시작한 이유’에 “사람의 요청: (본문)”과 요청으로 가는 연결을 보여 준다.
- 요청에서 생긴 `work.created` 사건은 사람이 시작한 일로 보고 새 연쇄(깊이 0)를 시작한다. 자동 모드에서 접수 담당이 바로 등록한 업무는 `automated=true`로 기록하되, 원인 사건이 없으므로 깊이 0에서 시작한다.
- 부서가 없는 서비스에서는 부서 없이 업무를 만든다. 담당자는 제안의 담당자, 없으면 비워 두고 계획 단계에서 정한다.

### 4.5 회사 조치

조치는 앱에 정해 둔 목록에서만 고른다. AI가 경로·명령을 정하지 않는다. 모든 조치는 서비스 모드와 관계없이 사람이 ‘내 할 일’에서 승인해야 실행한다.

| 조치 | 매개변수(접수 담당이 정함) | 승인할 때 사람이 정하는 것 | 실행 내용 |
|---|---|---|---|
| `deliver_code` 코드 결과 전달 | 실행 ID | 전달 방식, 폴더(필요할 때) | 4.6절 |
| `save_result` 결과 파일 저장 | 결과(산출물) ID | 저장 위치 | 기존 `SaveArtifactAs` |
| `export_service` 서비스 내보내기 | 없음 | 저장 위치 | 기존 `ExportProject` |
| `start_workflow` 흐름 실행 | 확정된 흐름 버전 ID | 없음 | 기존 `StartRun` |

- 승인 화면에는 접수 담당이 정한 매개변수, 이유, 실행하면 바뀌는 것(쓰는 폴더, 만드는 브랜치, 예상되는 비용 여부)을 보여 준다.
- 실행 결과(성공·실패와 이유, 만든 경로·브랜치)를 처리 항목에 저장하고 요청 상세에 보여 준다. 실패한 조치는 같은 승인 화면에서 다시 실행할 수 있다.
- 같은 처리 항목은 한 번만 실행한다. 실행 중 앱이 꺼지면 다시 켰을 때 ‘결과 확인 필요’로 두고 자동으로 다시 실행하지 않는다.
- 조치는 같은 서비스의 실행·결과·흐름만 가리킬 수 있다. 서비스 범위 검사(`storage/scope.go`)를 거친다.

### 4.6 코드 결과 전달

이 기능은 접수와 별도로 실행 화면의 버튼으로도 쓸 수 있게 만든다. 접수의 `deliver_code` 조치는 같은 함수를 부른다.

**최종 코드 계산**

1. 성공한 실행의 코드 단계마다, 마지막 세대에서 성공한 시도의 작업 공간 커밋(`workspaces.commit_sha`, `kind='code'`)을 모은다.
2. 다른 커밋의 조상인 커밋을 뺀다(`IsAncestor`). 남은 커밋이 하나면 그것이 최종 코드다.
3. 둘 이상이면 앱 저장소 안의 임시 작업 트리에서 차례로 합쳐 `agent-office/<실행>/final` 브랜치에 합치기 커밋을 만든다. 충돌이 나면 전달을 멈추고, 충돌 파일 목록과 함께 “충돌 해결” 업무를 만들 수 있게 안내한다.
4. 코드 단계가 없거나 실행이 성공하지 않았으면 전달할 수 없다고 알린다.

**전달 방식**

| 서비스 상태 | 방식 | 하는 일 |
|---|---|---|
| 작업 폴더 없음(앱 저장소) | 기준 코드 갱신(항상) | 앱 저장소의 `master`를 최종 코드로 옮긴다. 빨리 감기가 안 되면 합치기 커밋을 만들고, 충돌이면 멈춘다. 앱만 쓰는 저장소이므로 사람 폴더를 건드리지 않는다 |
| 작업 폴더 없음 | 폴더로 꺼내기(선택, 기본 켬) | 사람이 고른 **비어 있거나 없는** 폴더에 앱 저장소를 복제하고 `master`를 꺼낸다. 원격(`origin`) 연결은 지운다. ‘이 폴더를 서비스 작업 폴더로 쓰기’(기본 켬)를 고르면 서비스의 작업 폴더로 등록한다 |
| 작업 폴더가 Git 저장소 | 결과 브랜치 만들기(항상) | 사용자 저장소에 `agent-office/result-<실행 앞 8자>` 브랜치를 최종 코드로 만든다. 같은 이름이 있으면 번호를 붙인다. 작업 트리와 현재 브랜치는 그대로 둔다 |
| 작업 폴더가 Git 저장소 | 현재 브랜치에 반영(선택, 기본 끔) | 작업 트리가 깨끗하고 빨리 감기가 될 때만 현재 브랜치를 최종 코드로 옮긴다. 조건이 맞지 않으면 이유를 보여 주고 브랜치 만들기만 한다 |
| 작업 폴더가 Git 저장소가 아님 | 전달 불가 | 결과가 이미 그 폴더에 있다고 안내한다(공유 폴더 실행) |

- 전달 기록(실행, 최종 코드, 방식, 폴더·브랜치, 시각)을 실행 사건으로 저장하고 실행 화면의 ‘코드 결과’에 보여 준다. 같은 실행을 다시 전달할 수 있다(다른 폴더 등).
- 작업 폴더를 등록하면 이후 실행은 기존 규칙대로 그 폴더의 저장소에서 시작한다. 앱 저장소는 지우지 않는다.
- 접수 판단 입력에는 ‘서비스 기준 코드가 마지막 성공 실행의 최종 코드를 포함하는지’를 넣는다. 포함하지 않는 상태에서 코드 업무를 제안하면, 접수 담당이 먼저 `deliver_code`를 제안하도록 지시한다.

### 4.7 중복·재시작·화면 갱신

- 요청 하나의 판단 작업은 회차별로 하나다(`UNIQUE(request_id, round)`). 처리 항목은 판단·순번별로 하나, 업무는 처리 항목별로 하나, 하위 요청은 넘김 처리 항목별로 하나다.
- 앱 시작 때 기존 AI 작업 복구가 접수 판단도 복구한다. 결과는 저장됐는데 처리 항목이 없으면 저장된 결과로 마무리하고 다시 호출하지 않는다.
- 서비스 요청은 `request.*` 사건(`request.received`·`request.resolved`)을 그 서비스에 남긴다. 부서 구독 대상이 아니며 전달을 만들지 않는다. 회사 요청은 서비스가 없어 사건을 남기지 않고, 상태가 바뀔 때 Wails 런타임 이벤트(`requests:changed`)로 화면을 갱신한다.
- 새 판단 결과, 사람의 결정이 필요한 처리 항목, 조치 실행 결과는 ‘내 할 일’에 들어가고 기존 새 할 일 알림 설정을 따른다.

| 아래 표는 1차 설계다. 실제 구조는 `0017_requests.sql`: `intake_desks`, `requests`(요청 자체가 AI 작업, `round`·`max_attempts`), `request_attempts`(호출 시도, 서비스 또는 회사), `request_items`(`round`·`position`별), `work_items.origin_request_id`. `work_ai_jobs`·`work_ai_attempts`는 바꾸지 않았다 | — | — | — |
| `intake_desks` | 2 | `organization_id`, `project_id`(회사 접수는 비움), `name`, `assignment_id`(서비스), `connection_id`·`model`(회사), `instructions`, `budget`(JSON, 회사), `enabled` | 회사 접수: `project_id IS NULL`인 행은 조직당 하나(부분 고유 색인). 서비스 접수: `UNIQUE(project_id)`, 배정은 `(assignment_id, project_id)`로 참조 |
| `requests` | 2 | `organization_id`, `project_id`(회사 요청은 비움), `parent_id`, `previous_id`, `parent_item_id`, `body`, `status`(4.2절), `outcome`(`answer`/`route`/`work`/`action`/`question`/`decline`), `answer`, `question`, `reply`, `reason`, `created_at`, `updated_at`, `closed_at` | `UNIQUE(parent_item_id)`(넘김 하나에 하위 요청 하나), `declined`·`failed`는 `reason` 필수, 하위 요청은 서비스 필수 |
| `request_items` | 2 | `request_id`, `project_id`, `job_id`, `position`, `kind`(`route`/`work`/`action`), `payload`(JSON), `status`(`proposed`/`accepted`/`rejected`/`running`/`done`/`failed`/`check`), `work_item_id`, `child_request_id`, `result`(JSON), `decision_note`, `decided_at` | `UNIQUE(job_id, position)`, `UNIQUE(work_item_id)` |
| `work_ai_jobs` 다시 만들기 | 3 | `kind`에 `intake` 추가, `request_id` 추가 | `intake`는 `request_id` 필수·전달 없음·회차 1 또는 2, `UNIQUE(request_id, round)`, 키 `intake:{request_id}:{회차}`. 5단계에서 `project_id`를 `intake`이고 회사 요청일 때만 비울 수 있게 한다(이때 `organization_id` 필수) |
| `work_ai_attempts` 다시 만들기 | 5 | `project_id` 비움 허용 | 작업과 같은 범위(서비스 또는 회사) |
| `work_items.origin_request_id` | 3 | 업무를 만든 요청 | 같은 서비스의 요청인지 코드에서 검사 |

`work_ai_jobs`를 다시 만들 때는 이를 참조하는 `work_ai_attempts`·`judgments`·`auto_starts`·`collab_requests`의 외래 키가 유지되는지 업그레이드 시험으로 확인한다. 방식은 `0005_diagram_artifacts.sql`(새 테이블 → 복사 → 삭제 → 이름 변경, 색인 재생성)을 따른다. 3단계와 5단계에서 두 번 다시 만들지 않도록, 3단계에서 회사 요청용 열과 CHECK까지 함께 넣어도 된다.

회사 접수 사용량은 `project_id`가 빈 `intake` 작업의 시도를 합산한다. 기존 서비스 예산 집계(`projectUsage`)는 서비스가 있는 시도만 센다.
